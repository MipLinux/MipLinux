# 01 · 概念模型

> 这篇文档回答「构建发行版到底在做什么」。读完它，后面所有工具和步骤都会变得可预测。

---

## 1. 三个环境，职责完全不同

新手最容易犯的错误是把这三者混为一谈。

| 环境 | 干什么 | 为什么必须是它 | 不是什么 |
|---|---|---|---|
| **构建环境**（systemd-nspawn 里的纯 Arch） | 运行 `mkarchiso` 产出 ISO | 需要 `pacman` / `pacstrap` / `mkinitcpio`，非 Arch 系发行版没有；且不能用宿主发行版自己的源（见 D3） | 不能测试产物 |
| **测试环境**（宿主机的 QEMU） | 引导 ISO、验证安装结果 | 需要能「引导」一块磁盘 | 不能构建 |
| **终验环境**（真机） | 验证 NVIDIA 驱动、畸形分区、双系统 | QEMU 测不了真实硬件 | 迭代慢，不用于日常开发 |

**关键约束：构建和测试必须在不同的地方进行。** 原因见第 4 节。

---

## 2. 「构建发行版」是一次软件构建

这个类比是准确的，请照着理解：

| 软件开发 | 本项目 |
|---|---|
| 源代码 | `profiledef.sh` + `packages.x86_64` + `pacman.conf` + `airootfs/` |
| 依赖声明 | 包清单 |
| **构建工具** | **`mkarchiso`** |
| 构建环境 | systemd-nspawn 中的纯 Arch |
| 产物 | `miplinux-<版本>-x86_64.iso` |
| 拼写检查 | `shellcheck`（archiso 自带目标） |
| **验收测试** | **从产物引导起来** |

### 但「编译」这个词要打折扣

因为绝大多数包都是**预先编译好的二进制**，`mkarchiso` 的流水线里只有一步是真正的「构建」：

```
mkarchiso 流水线
├─ pacstrap       → 解压已编译的二进制包     ← 装配
├─ 复制 airootfs  → 文件覆盖                  ← 装配
├─ mkinitcpio     → 生成 initramfs            ← ★ 唯一的「编译」
├─ mksquashfs     → 压缩整个系统              ← 装配
└─ xorriso        → 组装成 ISO                ← 装配
```

**这个区别有实际意义：**

- 构建很快（几分钟，不是几小时）
- 可以放心地频繁重建，改一行配置重建一次的成本极低
- 如果将来引入 DKMS（自维护内核模块），那里会出现真正的编译，构建时间会显著上升

## 3. Live 环境是怎么跑起来的

理解这一点，才能理解为什么「在 Live 里装东西」毫无意义。

```
ISO 里的 airootfs.sfs（squashfs 格式）
        │
        │  ← 只读，压缩存储，节省体积
        ▼
   启动时挂载
        │
        ├─ 读操作 → 读 squashfs
        └─ 写操作 → 写到内存中的 overlay 可写层
```

**结论：**

- Live 环境的任何修改都只在内存里，**重启全部还原**
- Live 环境适合做「安装前的准备」和「救援」，不适合做持久化工作
- 这也是为什么安装器必须把东西写到**目标磁盘**上，而不是就地配置

---

## 4. 为什么 nspawn 不能测试 ISO

这是本项目最容易搞错的一点，单独强调。

`mkarchiso` 的产物是**可引导介质**——它包含引导器、分区表、内核、initramfs。

> **`systemd-nspawn` 不会「引导」任何东西。**

nspawn 的工作方式是：共享宿主机内核，直接运行某个目录里的 `systemd`。它根本没有「引导」这个概念，所以拿它测 ISO 是方向性错误。

nspawn 测不了、恰好也是最需要验证的东西：

| 要验证的 | nspawn | QEMU |
|---|---|---|
| 包是否装进 squashfs | ✅ | ✅ |
| 文件权限是否正确 | ✅ | ✅ |
| **BIOS/UEFI 能否引导** | ❌ | ✅ |
| **initramfs 能否挂载 squashfs** | ❌ | ✅ |
| **overlay 读写层是否正常** | ❌ | ✅ |
| **安装器能否分区、写引导** | ❌ | ✅ |
| **装完的系统能否启动** | ❌ | ✅ |

## 5. Arch 没有 stage3，但有类似物

如果你接触过 Gentoo，会自然地问「stage3 在哪」。

**Arch 有对应产物，但用途不同。**

`mkarchiso` 支持三种构建模式（源码 `-m [mode ..]` 的说明）：

```
valid modes are: 'bootstrap', 'iso' and 'netboot'
```

对应 profile 里可以有两份包清单：

| 文件 | 内容 | 产物 |
|---|---|---|
| `bootstrap_packages` | `arch-install-scripts`、`base` | `xxx-bootstrap-<版本>-x86_64.tar.zst` |
| `packages.x86_64` | 完整包清单（releng 为 129 个） | 可引导 ISO |

### 但两者用途相反

| | Gentoo stage3 | Arch bootstrap tarball |
|---|---|---|
| 性质 | **种子**，之后靠 `emerge` 生长 | **成品形态**的根文件系统 |
| 获取软件 | 本地编译 | 直接安装预编译二进制 |
| 编译器地位 | 核心工具 | 基本不参与 |

**对本项目的结论：**

- 交付物必须是 **ISO**，因为目标是「插上 U 盘就能装」，而 bootstrap tarball 不是可引导介质
- bootstrap tarball 只有两个用途：给 systemd-nspawn 当环境基底、给高级用户做 chroot 安装

## 6. `airootfs` 这个名字的来历

**A**rch **I**SO **rootfs** —— Arch ISO 的根文件系统。

它就是「先装出一个完整系统，再压扁」这个流程的直接产物，也是运行时被 squashfs 承载的那个根。名字本身就是最好的提示。

---

## 7. 四条贯穿全局的原则

### 7.1 产物决定一切

配置文件写得再漂亮，**唯一的验收标准是从产物引导起来能用**。任何「看起来应该对」都不算数。

### 7.2 配置即事实

两人协作时，不靠「我这能跑」，靠「配置改了没有」。所有差异都应该体现在 git 里，而不是某台机器的状态上。

### 7.3 Live 与装后系统必须一致

Live 环境里能用的东西（中文输入法、N 卡驱动），装完之后必须一样能用。实现手段是**共用同一份包清单**。

如果两边各维护一份，迟早会出现「Live 里中文能打字、装完就不能」这类难以定位的问题。

### 7.4 逻辑先于外壳

装系统的实际逻辑（分区 → 装包 → 配置 → 写引导）无论在哪种安装器方案下都是同一套。

**先把这套逻辑写成脚本并在 QEMU 里跑通，再考虑套什么界面。** 这样任何界面方案的变更都不会导致返工。
