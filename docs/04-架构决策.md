# 04 · 架构决策

> 这篇文档记录 NVIDIA 驱动与中文支持的具体技术决策，以及背后的实测依据。
>
> 决策编号与 [README.md](../README.md) 的关键决策记录表对应。本文档展开其中与驱动、中文相关的部分（D4、D5、D6、P8）；D2、D3 的机制说明见 [02-环境与工具链.md](02-环境与工具链.md) 第 3 节。

## 第一部分 · NVIDIA 驱动

### 1.1 前提：NVIDIA 打包已进入新时代

包名发生了根本变化，实测 Arch 官方仓库现状：

| 包名 | 状态 |
|---|---|
| `nvidia` | **已不存在** |
| `nvidia-dkms` | **已不存在** |
| `nvidia-lts` | **已不存在** |
| `nvidia-open` | ✅ extra/615.71.09-3 |
| `nvidia-open-dkms` | ✅ extra/615.71.09-1 |
| `nvidia-open-lts` | ✅ extra/615.71.09-3 |
| `nvidia-utils` | ✅ extra/615.71.09-1 |

原因：**NVIDIA 590 起，主线包切换到 Open Kernel Modules，同时移除了 Pascal 及更老架构的支持。**

参考资料：

- [Arch Linux News: NVIDIA 590 driver drops Pascal and lower support; main packages switch to Open Kernel Modules](https://archlinux.org/news/nvidia-590-driver-drops-pascal-support-main-packages-switch-to-open-kernel-modules/)
- [Phoronix: Arch Linux's Main NVIDIA Driver Packages Now Using The Open Kernel Modules](https://www.phoronix.com/news/Arch-LInux-NVIDIA-Open-Default)

### 1.2 决策 D5：不使用 CachyOS 内核或其仓库

**决定：不挂载 CachyOS 或其它第三方软件源。**

理由：

- 项目起因之一就是对 CachyOS 的现状不满，依赖其仓库在目标上自相矛盾
- 引入外部源会破坏构建的确定性与可复现性
- CachyOS 的 `linux-cachyos-nvidia-open` 不在官方仓库，一旦依赖它，ISO 的构建就必须联网访问该源

**直接技术后果：** 由于 `nvidia-open` 硬绑官方内核（详见下一节），D4 与 D5 是同一个决定的两面。

### 1.3 关键约束：`nvidia-open` 硬绑官方内核

实测依赖关系：

```
nvidia-open       依赖  ['libglvnd', 'linux', 'nvidia-utils=615.71.09']
nvidia-open-dkms  依赖  ['dkms', 'nvidia-utils=615.71.09']
```

`nvidia-open` 的依赖中有两个字面量：

- **`linux`** —— 硬绑官方 `linux` 内核
- **`nvidia-utils=615.71.09`** —— 锁死配套版本

**这意味着：一旦使用非官方内核（如 CachyOS 内核），`nvidia-open` 立刻不可安装。**

### 1.4 决策 D4：使用官方 `linux` 内核

**决定：内核使用官方 `linux`，NVIDIA 驱动使用 `nvidia-open`。**

理由：

| 理由 | 说明 |
|---|---|
| 零额外工作 | 模块由官方预编译，无需 DKMS 编译，Live 环境直接可用 |
| 不引入外部仓库 | 不需要挂载 CachyOS 或其它第三方源 |
| 与项目目标一致 | 项目起因之一就是不想依赖 CachyOS |
| 构建确定性 | 官方源的包版本可预测 |

**被否决的方案：**

| 方案 | 否决理由 |
|---|---|
| CachyOS 内核 + `nvidia-open-dkms` | 需要挂载 CachyOS 仓库，与项目目标冲突；且其 `linux-cachyos-nvidia-open` 不在官方源 |
| 使用 DKMS 通用方案 | Live 环境中 DKMS 编译会占用内存和时间，且 squashfs 是只读的 |
| 自定义内核 | 需要自建仓库分发预编译模块，超出当前阶段范围 |

### 1.5 实测确认的配置细节

以下在本机实际检查得到，是配置 ISO 时的直接依据。

#### 1.5.1 `nouveau` 已被自动屏蔽

`/usr/lib/modprobe.d/nvidia-utils.conf` 的内容：

```
# Blacklist nouveau and nova
blacklist nouveau
blacklist nova_core
blacklist nova_drm
# Make sure that all modules are loaded after the main one.
softdep nvidia post: nvidia-uvm nvidia-drm
options nvidia NVreg_UseKernelSuspendNotifiers=1 NVreg_TemporaryFilePath=/var/tmp
```

**结论：安装 `nvidia-utils` 后，开核驱动与 nouveau 的冲突已被自动处理，且模块加载顺序已通过 `softdep` 声明。这部分不需要额外配置。**

#### 1.5.2 `nvidia_drm.modeset=1` 必须手动设置

实测结果：**`nvidia_drm.modeset=1` 没有出现在任何 modprobe 配置或 modules-load 配置中。**

当前宿主机的内核命令行是：

```
quiet nowatchdog splash rw rootflags=subvol=/@ root=UUID=... initrd=\initramfs-linux-cachyos.img
```

注意：**连 CachyOS 自己也没有设置这个参数。**

**结论：`nvidia_drm.modeset=1` 必须由我们自己写进 ISO 的引导配置。**

需要修改的位置：

- `efiboot/loader/entries/*.conf` 的 `options` 行（UEFI）
- `syslinux/archiso_sys-linux.cfg` 对应行（BIOS）

**为什么必须设置：** Wayland 会话需要 DRM 内核模式设置。不设置的情况下，Wayland 合成器无法正常工作。

#### 1.5.3 已无 NVIDIA 相关的 pacman hook

实测 `/usr/share/libalpm/hooks/` 中**不存在** NVIDIA 相关 hook。

**结论：** 模块更新后不会自动重建 initramfs，行为与旧版本不同，不要依赖旧文档的说法。

#### 1.5.4 已安装的 NVIDIA 相关包（参考）

宿主机当前实际安装：

```
nvidia-utils              615.71.09-1
lib32-nvidia-utils        615.71.09-1
opencl-nvidia             615.71.09-1
lib32-opencl-nvidia       615.71.09-1
libva-nvidia-driver       0.0.18-1.1
nvidia-settings           615.71.09-1
nvidia-prime              1.0-6
linux-firmware-nvidia     1:20260910-1
linux-cachyos-nvidia-open 7.2.5-1
```

**注意最后一行**：宿主机的驱动来自 CachyOS 的内核包，而非 `nvidia-open`。这正说明了两种方案的不兼容性——宿主机上装的 `nvidia-utils` 可以由不同的内核模块包配套。

### 1.6 Live 环境中的 N 卡驱动

**Live 环境中 N 卡驱动不需要特殊的 initramfs 配置。**

原因：

- `mkinitcpio` 的 `modconf` 钩子加载 `/usr/lib/modules/` 中的模块
- 模块随内核包安装到 squashfs 中
- 启动后由 `softdep` 声明的顺序自动加载

**前提是** `nvidia-open` 和 `nvidia-utils` 都在 `packages.x86_64` 里，且内核版本匹配。

### 1.7 待确认的覆盖范围（P8）

**`nvidia-open` 已不支持 Pascal 及更老架构（GTX 10 系及以前）。**

如果目标用户中包含老显卡用户，需要额外方案：

| 方案 | 代价 |
|---|---|
| 同时提供 legacy 驱动分支 | ISO 体积增加，需要 udev 规则按硬件选择模块 |
| 只支持 Turing 及更新架构 | 部分用户开机走 nouveau，体验下降 |
| 提示用户自行安装 | 违背「开箱可用」的初衷 |

**需确认两位开发者各自的显卡型号后再决定。**

## 第二部分 · 中文支持

中文支持不是一个包的事，需要分五层处理。

### 2.1 字体层

需要安装的包：

| 包名 | 用途 |
|---|---|
| `noto-fonts-cjk` | 思源黑体/宋体可变字体，主力 CJK 字体 |
| `adobe-source-han-sans-cn-fonts` | 备选，部分场景渲染更好 |
| `wqy-microhei` / `wqy-zenhei` | 轻量补充 |
| `noto-fonts-emoji` | **容易被忽略，但用户一开机就会看到** |
| `ttf-dejavu` 或等宽字体 | 终端中文字体 |

**字体配置不止是装包。** 还需要在 `/etc/fonts/local.conf` 中配置 `sans-serif` 的 CJK fallback 顺序，否则浏览器里中英混排的字重和字形会很难看。

**终端字体是另一个盲区** —— 等宽字体如果没有 CJK 覆盖，终端里的中文会显示为方块。

### 2.2 输入法层

| 组件 | 包名 |
|---|---|
| 框架 | `fcitx5` |
| RIME 引擎 | `fcitx5-rime` |
| 拼音方案 | `fcitx5-chinese-addons` |
| 配置界面 | `fcitx5-configtool` |
| 主题 | `fcitx5-material-color` 等 |

**三个必须处理的细节：**

1. **RIME 数据** —— `librime` 的默认方案数据需要额外拉取，否则首次启动没有可用输入方案
2. **Wayland 环境变量** —— 必须设置：
   ```
   GTK_IM_MODULE=fcitx
   QT_IM_MODULE=fcitx
   XMODIFIERS=@im=fcitx
   ```
   这套变量通过 `airootfs/etc/environment` 或 `~/.config/environment.d/` 注入
3. **自动启动** —— Wayland 会话下 fcitx5 需要常驻，通过 `~/.config/autostart/` 或 compositor 配置处理

### 2.3 本地化层

| 项目 | 内容 |
|---|---|
| `/etc/locale.gen` | 预生成 `zh_CN.UTF-8` |
| `/etc/locale.conf` | `LANG=zh_CN.UTF-8` |
| `/etc/vconsole.conf` | 控制台字体与键盘布局 |
| 时区 | `Asia/Shanghai` |
| `/etc/skel/` | 新用户默认的 `.bashrc`、`.xprofile` 等 |

### 2.4 网络层（优先级最高）

**这一条对中文用户的实际影响超过其它所有层。**

官方源在国内的直接后果是安装速度慢到不可用。处理方式见 [03-项目结构.md](03-项目结构.md) 第 4 节。

**关键要求：**

> 安装完成后，**目标系统也必须继承国内镜像源**。

只在 Live 环境生效是不够的——用户装完之后第一次 `pacman -Syu` 就会退回到官方源。

这是 CachyOS 最劝退中文用户的地方之一，也是本项目的核心差异化点。

**已验证可用的镜像：**

- 清华 TUNA：`https://mirrors.tuna.tsinghua.edu.cn/archlinux/`
- 中科大 USTC：`https://mirrors.ustc.edu.cn/archlinux/`
- 阿里云：`https://mirrors.aliyun.com/archlinux/`

### 2.5 文档层

装完后提供一份中文上手说明。

**经验判断：这比多预装一个软件更有价值。** 中文用户遇到问题的第一障碍是找不到中文资料，一份准确的本地文档能显著降低挫败感。

形式可以是：

- 写入 `~/.config/` 或桌面上的一个文本文件
- Live 环境中的一个命令（如 `miplinux-guide`）
- 项目仓库中的在线文档

## 第三部分 · 一致性要求

### 3.1 单一包清单

Live 环境与安装器写盘时**必须使用同一份包清单**。

这是 [01-概念模型.md](01-概念模型.md) 第 7.3 节「Live 与装后系统必须一致」原则的落地要求，也是 [03-项目结构.md](03-项目结构.md) 第 7.1 节强调的约束。

### 3.2 镜像源的双重生效

镜像源需要在两个地方生效：

| 位置 | 目的 |
|---|---|
| profile 的 `pacman.conf` | 构建时使用国内源拉包 |
| `airootfs/etc/pacman.d/mirrorlist` | 装后系统继承国内源 |

两者不能只做一半。
