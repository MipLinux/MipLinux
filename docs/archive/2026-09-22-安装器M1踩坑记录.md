## 一、结论先行的三条口径

1. **判据的优先级：内核 > 设备节点 > `lsblk`。**
   `/proc/partitions` 与 `/sys/block/` 是内核的事实；`/dev/*` 是设备节点（可能滞后或被删）；
   `lsblk` **会把「盘上的分区表里写着、但内核没收下」的分区也列出来** —— 它自己去读设备。
   照 `lsblk` 的名单去 `mkfs`，就会得到一句 `No such file or directory`。
2. **静默成功比失败更贵。** 本轮两次栽在"退出码 0 但什么都没做"上：
   `chpasswd` 读到空输入时什么都不做却退 0；`wipefs` 在 udev 没跟上的时候报的错又完全指不到 udev。
   → 关键步骤都要**回头断言**它真的生效了（`passwd -S` = `P`、`blkid` 真读到 UUID、loader entry 里的 UUID 与盘一致）。
3. **别解析 `lsblk` 的文本。** 它的树线（`└─`）**在管道里也会输出** ——
   `awk '$2 == "part" { p = $1 }'` 取到的是 `└─/dev/vda2`，`mount` 拿到这种路径就失败。
   必须带 `-l`（list 模式），或者干脆改看 sysfs（本项目的安装器已经这么做了）。
4. **别凭记忆写别人的 API。** pyparted 的公开 API 是 camelCase，而底层 `_ped` 是 snake_case；
   记忆里的 `get_device` 根本不存在。每验证一次要跑一轮 QEMU（约 10 分钟 + 人的时间），
   所以「先看上游源码」不是洁癖，是省时间。

## 二、构建脚本侧（属线 E / `scripts/`，已分流成 issue）

这三条不在本线文件里，全部走 issue，没有夹带在 PR 里。

### 2.1 `mipl build` 在成功路径上必炸（#38）

- **症状**：bootstrap 下载并**校验通过之后**立刻退出 127：
  `baseline-build.sh: 行 706: file_size: 未找到命令` / `ok: 未找到命令`。
- **根因**：`ok()` / `file_size()` 只定义在 `mipl.sh`，而 `mipl.sh` 是用
  `run_root env … "$script"` **另起进程**跑 `baseline-build.sh` 的 —— bash 函数不会跟过去。
  `baseline-build.sh` 只 source 了 `mipl-lib.sh`（里面只有 `mipl_*` 函数）。
  调用点 655 / 672 / 706 / 795 **全在成功路径上**，所以自 `5883219` 起 `mipl build` 跑不完。
- **证据**：最后一次成功构建是 2026-09-21 19:02 的 `miplinux-2026.09.21`，回归提交是当天 20:13。
- **当时的绕法**：用 `BASH_ENV` 注入两个只做打印的同名函数（不改仓库），构建随即成功 —— 反证了失败点与 ISO 内容无关。
- **修法**：把那组显示函数挪进 `mipl-lib.sh` 供两个脚本共用。

### 2.2 冷缓存时从不取 `sha256sums.txt`（#39）

- **症状**：冷缓存下连续下载三次 bootstrap，每次报「本地还没有 sha256sums.txt，无从对照」，最后 die。
- **根因**：取校验和清单那段写在 `if [[ -f "$BOOTSTRAP_FILE" ]]`（**已存在缓存**）分支里；
  冷启动直接进下载循环，清单从没取过 → `checksum_ok` 永远无法对照。热缓存反而正常，所以一直藏着。
- **证据**：手动把清单放到脚本期望的路径后，同一条命令立刻通过校验。
- **修法**：把取清单提到下载循环之前。

### 2.3 `airootfs/etc/pacman.conf` 里的 `=======`（#40）

- **症状**：Live 与**装后系统**里每次 `pacman` 都念一句
  `directive '' in section 'archlinuxcn' not recognized`（中文环境是「无法识别指令」）。
- **根因**：`5883219` 留下的合并残片（第 40 行一行 `=======`），同一次改动还去掉了结尾换行。
  它本身只是警告（四个仓库照常更新），但安装器会把这个文件**原样复制进装后系统**，
  所以每个装完的用户都会看到一次。
- **修法**：删掉该行、补回结尾换行；`[archlinuxcn]` 段里「硬编码 Server + Include mirrorlist」
  两套写法要不要去掉一套，按 P11 一起定。

## 三、安装器侧（本线，已修）

### 3.1 pyparted 的 API 名（`get_device` → `getDevice`）

- **症状**：Live 里第一次真跑，`wipefs` 与守卫都对，卡在分区那一步：
  `module 'parted' has no attribute 'get_device'`。
- **根因**：凭记忆写的名字。pyparted 的公开 API 是 camelCase：`getDevice()`、`freshDisk(dev, "gpt")`、
  `Disk.commit()`；`Constraint` 还**只认关键字参数**（`Constraint(dev)` 会抛"missing initialization parameters"）。
- **修法**：照上游源码与 archinstall 的用法逐条改；新增 `tests/test_parted_api.py` ——
  把「我们依赖哪些 pyparted 名字」写成名单，名单外的名字直接红灯，snake_case 也直接红灯。
- **教训**：对「装不进本地环境、只能到 Live 里才能验」的第三方库，用一份**契约测试**把假设钉住，
  比在代码里写防御性 try/except 有用得多。

### 3.2 拿 `lsblk` 的输出当分区判据

- **症状**：`mkfs.vfat /dev/vda1` 报 `No such file or directory`，可 `lsblk -f /dev/vda` 明明列着 `vda1`/`vda2`。
- **根因**：`lsblk` 列的是「盘上分区表里写着的」，不等于「内核收下了、`/dev` 里有节点」。
  两轮排查都被它带偏（一度以为是 udev 的问题）。
- **修法**：新增 `kernel_partitions()` 读 `/sys/block/<盘>/<分区>/partition` 与 `dev`，
  删掉基于 `lsblk` 的解析函数 —— 判据本身就是错的，留着只会再被用一次。
- **教训**：**选错判据比写错代码更难查**，因为它每次都"有输出、看起来合理"。

### 3.3 内核收下了，`/dev` 里却没有节点

- **症状**：分区表提交后 `lsblk` 能看到两个分区，但 `/dev/vda1` 不存在，`mkfs` 报 ENOENT。
- **根因**：设备节点要等 udev 处理完 uevent；实测能滞后几十秒，等不起。
- **修法**：先 `partprobe` + `udevadm trigger --subsystem-match=block` + `settle`，
  再轮询 `os.path.exists`；**内核已经有了、节点仍然没有就自己 `mknod`**（这正是 udev 会做的事，
  同名同 major:minor，不冲突）。
- **教训**：`lsblk`（sysfs）、`/dev` 节点、`/proc/partitions` 三者可以互相不一致，别把它们当成一件事。

### 3.4 动盘之前必须先让 udev 追平

- **症状**：分区表在、`/dev/vda1` 在、`/proc/partitions` 也认，但
  `wipefs -a /dev/vda1` 报 `probing initialization failed: No such file or directory`。
- **根因**：这是 libblkid 在 udev 还没处理完这块设备时的表现 —— **报错文本完全指不到 udev**。
- **证据**：同一台 Live 里手工跑 `udevadm trigger --subsystem-match=block; udevadm settle` 之后，
  之前失败的 `wipefs -a /dev/vda1` 立刻成功，`blkid` 也能读到 `PARTUUID`。
- **修法**：`settle_udev()` 放在**碰任何设备节点之前**（预擦循环之前），分区表提交后再来一次；
  预擦循环跳过没有设备节点的分区（对不存在的路径 `wipefs` 只会白跑一轮）。
- **教训**：报错文本指向的层，往往不是出问题的那一层。`wipefs` 说"文件不存在"，真凶是 udev 没排上队。

### 3.5 真凶：root 压到了盘尾的 GPT 备份表头

- **症状**：与前两条同款 —— 内核里**只有 `vda1`**，没有 `vda2`；节点自然也没有。
- **根因**：布局把 root 算到了**盘的最后一个字节**，而 GPT 把**备份表头**放在盘尾那 33 个扇区里。
  分区压上去之后，内核要么把它裁短、要么干脆不收下。
- **证据**：`/proc/partitions` 只列出 `vda1`；同一块盘用 `parted` CLI 建的 `100%` 分区则被内核**裁掉了 1 MiB**
  （`41416704` vs `41417728` KiB）—— 两次行为不同，但都指向"不许压到盘尾"。
- **修法**：`plan_layout()` 留出 `GPT_TAIL_RESERVE = 1 MiB`，并加回归测试
  （`test_root_leaves_room_for_the_backup_gpt`）钉死。同时把超时报错改成说**内核的视图**：
  「内核只收下了 N 个分区」并点明这个常见原因。
- **教训**：分区表是**有规格的**（GPT 主表头 + 备份表头各占 33 扇区）。
  自研分区最先该做的不是写代码，而是把规格里那几处"不许碰"的地方列出来。

### 3.6 root 密码：我擅自留成锁定，还不说

- **症状**：装完的系统 root 登不进去（当然），但**安装器一个字都没提**。
- **根因**：不是技术 bug，是**替用户做了决定**：我在代码注释里写了「root 不设密码（锁定）」，
  却没有任何输出告诉用户这件事，也没给开关。
- **修法**：新增 `--root-password-stdin`（两行密码按「用户在前、root 在后」从 stdin 读，都不进 argv）；
  不给这个开关就保持锁定，但**明说**，收尾还打印账号状态。
- **教训**：默认值可以保守，但**保守的默认值必须被说出来**。
  一个"静默的锁定"和一个"静默的失败"是同一种错误。

### 3.7 `keep_log` 静默失败：树线路径 + `|| true` 把错误吞了

- **症状**：排练脚本说「日志也留了一份在装后系统的 `/root/` 下」，实际那台系统里**没有**这个文件。
- **根因**：`root_part="$(lsblk -pno NAME,TYPE … | awk …)"` —— 少了 `-l`，
  而 `lsblk` 的树线在管道里照旧输出，于是 `mount "└─/dev/vda2" /mnt` 失败；
  失败又被行尾的 `2>/dev/null || true` 吞掉，整件事**没有任何输出**。
- **证据**：主机上一条命令就能复现：
  `lsblk -pno NAME,TYPE /dev/nvme1n1 | awk '$2=="part"{p=$1} END{print p}'` → `└─/dev/nvme1n1p4`；
  加 `-l` 之后 → `/dev/nvme1n1p4`（`lsblk -lpno …`）。
- **修法**：加 `-l`；挂载点改成参数（可测）；新增 `tests/test_rehearsal_script.py` ——
  用桩 `lsblk`（**会分辨有没有 `-l`**，像真的一样）断言 `mount` 拿到的是干净路径、
  日志真的落到目标的 `/root/` 下。把 `-l` 去掉，这个测试会红。
- **教训**：`2>/dev/null || true` 用在「失败了也无所谓」的地方是对的，
  但**「留一份日志」不是无所谓** —— 它恰恰是失败时最需要的东西。写的时候要想清楚这一句到底能不能失败。

### 3.8 Live 的 root shell 是 zsh：`BASH_SOURCE` 会把脚本炸掉

- **症状**：把排练脚本 `source` 进 Live 的 shell 做单点验证时，
  报 `live-rehearsal.sh:118: BASH_SOURCE[0]: parameter not set`。
- **根因**：Live 的 root shell 是 **zsh**（releng 带 `grml-zsh-config`），那里没有 `BASH_SOURCE`；
  而脚本头有 `set -euo pipefail`，`-u` 让未定义变量直接报错。
- **修法**：判断「是不是被 source 的」改用环境变量（`MIPL_REHEARSAL_SOURCED`），
  不用 `BASH_SOURCE`，也不用 `$0`（zsh 在 source 时会把 `$0` 设成被 source 的文件，同样判不出来）。
- **教训**：Live 里跑的东西不能假定 shell 是 bash，哪怕脚本自己有 shebang ——
  一旦有人 `source` 它、或者把内容粘进交互 shell，环境就变了。

### 3.9 顺带加的防线：密码设没设上要问一句

- **症状**：没有症状 —— 这正是问题。`chpasswd` 读到空输入时**什么都不做却退出 0**，
  于是一路绿灯装完，重启谁也登不进去。
- **修法**：`verify_password()` 在 chroot 里跑 `passwd -S <用户>`，必须是 `P`（可用密码），
  否则退出码 5 停下；同时把目标盘 `/etc/shadow` 里的字段再看一眼。
- **教训**：凡是"退 0 就算成功"的外部命令，只要它的失败后果是**装出一个不能用的系统**，就得回头断言。

## 四、排查方法（这部分最值得复用）

### 4.1 自己开无头 QEMU，把"求人开窗口截图"变成几秒一轮

Live 里没有 ssh、也没有串口控制台，一开始只能请维护者开图形窗口、手敲命令、截图回来 ——
一轮十几分钟，而且每轮只能试一个假设。后来改成：

```bash
# 无头 QEMU + monitor socket（QEMU 仍以 root 跑，走 pkexec；socket 用 umask 000 让普通用户可连）
sudo env MIPL_QEMU_EXTRA="-display none -monitor unix:/tmp/mipl-mon,server=on,wait=off -drive file=/tmp/mipl-installer-src.iso,media=cdrom,readonly=on" \
  sh -c 'umask 000; exec ./scripts/mipl.sh qemu --disk <盘>'
# 截屏 / 往 TTY 打字（QEMU monitor 的 screendump 与 sendkey）
printf 'screendump /tmp/x.ppm\n' | socat - UNIX-CONNECT:/tmp/mipl-mon && convert /tmp/x.ppm /tmp/x.png
```

这样"看一眼 Live 现在什么状态"从十几分钟变成几秒，才可能在一次会话里连着试五六个假设。
（`docs/work/tech/02-构建与QEMU测试.md` 的 C.3 是它的手工版。）

### 4.2 把代码送进 Live 的更快通道

重新打 ISO → 重开 QEMU → 重挂光驱，一轮就是几分钟。改成宿主机起一个**只绑本机**的
`python3 -m http.server`，Live 里 `curl http://10.0.2.2:<port>/installer.tgz` 解到 `/run/` 再跑
（QEMU 用户网络里 `10.0.2.2` 就是宿主机的 loopback）。改一行代码到跑起来只要十几秒。

### 4.3 认盘的规矩

多挂一张 CD 之后，**启动用的 ISO 是 `sr1`、源码盘是 `sr0`**（与直觉相反）。
**按容量认盘，别按号猜**：那张几百 K 的 rom 才是源码盘。
（`installer/tests/make-src-iso.sh` 的注释里也写了这条。）
