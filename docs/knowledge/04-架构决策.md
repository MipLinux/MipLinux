## 第一部分 · NVIDIA 驱动

### 1.1 NVIDIA 打包的新变化

包名发生了根本变化：

| 包名 | 状态 |
|---|---|
| `nvidia` / `nvidia-dkms` / `nvidia-lts` | **已不存在** |
| `nvidia-open` / `nvidia-open-dkms` / `nvidia-open-lts` | 开核模块，主线包 |
| `nvidia-utils` | 配套的用户态工具 |

版本随时间滚动，要当前值查仓库（`pacman -Si nvidia-open`）。

原因：**NVIDIA 590 起，主线包切换到 Open Kernel Modules，同时移除了 Pascal 及更老架构的支持。**

参考资料：

- [Arch Linux News: NVIDIA 590 driver drops Pascal and lower support; main packages switch to Open Kernel Modules](https://archlinux.org/news/nvidia-590-driver-drops-pascal-support-main-packages-switch-to-open-kernel-modules/)
- [Phoronix: Arch Linux's Main NVIDIA Driver Packages Now Using The Open Kernel Modules](https://www.phoronix.com/news/Arch-LInux-NVIDIA-Open-Default)

### 1.2 决策 D5：不使用 CachyOS 内核或其仓库

**决定：不挂载 CachyOS 或其它第三方软件源。**

理由：

- 项目起因之一就是对 CachyOS 的现状不满，依赖其仓库在目标上自相矛盾
- 引入外部源会破坏构建的确定性与可复现性
- CachyOS 的 `linux-cachyos-nvidia-open` 不在官方仓库，一旦依赖它，ISO 的构建就必须联网访问该源

**直接技术后果：** 由于 `nvidia-open` 硬绑官方内核（详见下一节），D4 与 D5 是同一个决定的两面。

### 1.3 关键约束：`nvidia-open` 硬绑官方内核

`nvidia-open` 的依赖里有两个字面量（要当前值看 `pacman -Si nvidia-open`）：

- **`linux`** —— 硬绑官方 `linux` 内核
- **`nvidia-utils`（带精确版本号）** —— 锁死配套的用户态包版本

**这意味着：一旦使用非官方内核（如 CachyOS 内核），`nvidia-open` 立刻不可安装。**

### 1.4 决策 D4：使用官方 `linux` 内核

**决定：内核使用官方 `linux`，NVIDIA 驱动使用 `nvidia-open`。**

理由：

| 理由 | 说明 |
|---|---|
| 零额外工作 | 模块由官方预编译，无需 DKMS 编译，Live 环境直接可用 |
| 不引入外部仓库 | 不需要挂载 CachyOS 或其它第三方源 |
| 与项目目标一致 | 项目起因之一就是不想依赖 CachyOS |
| 构建确定性 | 官方源的包版本可预测 |

**被否决的方案：**

| 方案 | 否决理由 |
|---|---|
| CachyOS 内核 + `nvidia-open-dkms` | 需要挂载 CachyOS 仓库，与项目目标冲突；且其 `linux-cachyos-nvidia-open` 不在官方源 |
| 使用 DKMS 通用方案 | Live 环境中 DKMS 编译会占用内存和时间，且 squashfs 是只读的 |
| 自定义内核 | 需要自建仓库分发预编译模块，超出当前阶段范围 |

### 1.5 实测确认的配置细节

以下在本机实际检查得到，是配置 ISO 时的直接依据。

#### 1.5.1 `nouveau` 已被自动屏蔽

`nvidia-utils` 自带一份 modprobe 配置，把 `nouveau`（及同族模块）列入黑名单，并用 `softdep` 声明
模块加载顺序。

**结论：安装 `nvidia-utils` 后，开核驱动与 nouveau 的冲突已被自动处理，且模块加载顺序已通过 `softdep` 声明。这部分不需要额外配置。**
要看当前那份配置的原文：`/usr/lib/modprobe.d/nvidia-utils.conf`（包升级会改它，所以文档不抄）。

#### 1.5.2 `nvidia_drm.modeset` 默认开启，无需手动设置

实测结果：**`nvidia_drm.modeset=1` 没有出现在任何 modprobe 配置、modules-load 配置或内核命令行中，运行时仍为启用状态。**
也就是说这不是「某处配了它」，而是驱动**默认值就是 1** —— 不需要我们补配置。

**结论：目标 Arch 内核与 `nvidia-open` 组合中，`nvidia_drm.modeset` 默认值为 1，不需要由我们写进 ISO 的引导配置，也不需要额外的 modprobe 配置。**

如果将来为了覆盖默认值而显式声明，模块参数的正确写法是 `nvidia_drm.modeset=1`；但当前方案不添加这行。需要显式传递内核参数时，才修改：

- `efiboot/loader/entries/*.conf` 的 `options` 行（UEFI）
- `syslinux/archiso_sys-linux.cfg` 对应行（BIOS）

**验证方式：** 以运行时值为准：`cat /sys/module/nvidia_drm/parameters/modeset` 应输出 `Y`。不能把引导配置里是否出现这段文本当成验证依据。

#### 1.5.3 内核或驱动更新时，initramfs 会自动重建

**结论：不需要我们写任何 initramfs 相关的逻辑，`mkinitcpio` 包自带的 hook 已经覆盖了这些场景。**

`mkinitcpio` 装了一条 pacman hook，**内核更新**（`usr/lib/modules/*/vmlinuz`）、**DKMS 编译**
（`usr/src/*/dkms.conf`，走 DKMS 的 NVIDIA 模块落在这里）与 `usr/lib/modprobe.d/` 变动都会触发
initramfs 重建。想自己核对当前触发条件：`/usr/share/libalpm/hooks/` 下的 `*mkinitcpio*` 文件。

**但驱动能不能用并不依赖 initramfs** —— 见 1.6：`modconf` 钩子让模块从 `/usr/lib/modules/` 加载，
所以驱动只需与内核版本匹配，不需要进 initramfs。

#### 1.5.4 模块包与用户态包可以不同源

**结论：`nvidia-utils` 不绑定内核模块包** —— 同一个 `nvidia-utils` 可以由不同的内核模块包配套（官方的 `nvidia-open`、
或发行版自编译的内核模块）。这正说明两种方案互不兼容：一旦换了内核模块的来路，用户态这一半不用动，但那已经不是 D4 的方案了。

### 1.6 驱动装在哪：由安装器写进装后系统

ISO 只承载 Live 环境，装系统所需的包在安装时从仓库拉取。**N 卡驱动的落点因此是装后系统**：
安装器在装包阶段装上 `nvidia-open` + `nvidia-utils`，用户装完重启拿到的就是带驱动的系统。

**驱动不需要任何特殊的 initramfs 配置**，机制与它装在哪个环境无关：

- `mkinitcpio` 的 `modconf` 钩子加载 `/usr/lib/modules/` 中的模块
- 模块随内核包安装
- 启动后由 `softdep` 声明的顺序自动加载

需要确认的只有一件：**内核版本与驱动包匹配**（`nvidia-open` 硬绑官方 `linux`，见 1.3）。

**验证点因此在「装完重启之后」** —— 真机验证要装到盘上、从盘启动，再看驱动有没有加载
（[05-测试方法.md](05-测试方法.md) 检查点 4、5）。

### 1.7 装后驱动覆盖范围：Turing 及更新

**决定（D8）：装后系统只覆盖 Turing 及更新架构。** 几位长期开发者的显卡（Blackwell / RTX 50 系、Ada Lovelace / RTX 40 系）都落在这个范围内。

**背景：** `nvidia-open` 已不支持 Pascal 及更老架构（GTX 10 系及以前）。

**技术确认：Blackwell 属于 Turing 及更新的范围，`nvidia-open` 完全支持，无需任何 legacy 处理。**

| 方案 | 代价 | 本项目 |
|---|---|---|
| **装后只支持 Turing 及更新；Live 为旧卡保留 nouveau 回退** | Live 在安装器启动前尝试为未绑定驱动的 NVIDIA 显示设备显式加载 nouveau；装后不提供旧卡驱动 | ✅ 采用（Issue #44） |
| 同时提供 legacy 驱动分支 | ISO 体积增加，需要 udev 规则按硬件选择模块 | ❌ 不做 |
| 提示用户自行安装 | 违背「开箱可用」的初衷 | ❌ 不做 |

**对外口径：** Live ISO 为 Pascal 及更老的显卡保留 nouveau 回退路径；装后系统只支持 Turing 及更新架构，旧卡不在支持范围内。

Live 的 fallback 由 `mipl-nouveau-fallback.service` 在 `mipl-installer.service` 前运行。它等待 udev 探测完成，只对仍未绑定驱动的 NVIDIA 显示 / 3D 设备显式执行 `modprobe nouveau`；这样保留 `nvidia-utils` 对 nouveau 别名自动加载的 blacklist。旧款 NVIDIA 显卡的 Live 启动路径尚未在实机上验证。

**副作用：** 由于两位开发者的显卡本身就在目标范围内（Blackwell、Ada Lovelace），**真机验证可以覆盖实际用户的典型硬件**，不必额外寻找测试设备。

## 第二部分 · 中文支持

中文支持不是一个包的事，需要分五层处理。

### 2.1 字体层

两个环境用的字体不同，但 fallback 规则只有一份（Live 的 `/etc/fonts/local.conf`，由安装器复制进装后系统）：

| 包名 | 用在哪 | 用途                   |
|---|---|----------------------|
| `noto-fonts-cjk` | Live + 装后 | 思源黑体/宋体，主力 CJK 字体    |
| `noto-fonts-emoji` | Live + 装后 | 表情包                  |
| `ttf-maplemono` 系 | 装后 | 终端与代码用的等宽字体，带 CJK 覆盖 |
| `terminus-font` | Live | 控制台字体                |

**字体配置不止是装包。** `/etc/fonts/local.conf` 同时配 `sans-serif` 与 `monospace` 的 CJK fallback 顺序：
只配前者，终端与代码块里的中文就会显示为方块。这份配置由安装器写进装后系统，两边不会各配一套。

### 2.2 输入法层

装后系统列入的包：

| 组件 | 包名 |
|---|---|
| 框架 | `fcitx5` |
| 中文输入方案 | `fcitx5-chinese-addons` |
| 配置界面 | `fcitx5-configtool` |
| 各工具包集成 | `fcitx5-gtk` · `fcitx5-qt` |

**两个必须处理的细节：**

1. **Wayland 环境变量** ：
   ```
   GTK_IM_MODULE=fcitx
   QT_IM_MODULE=fcitx
   XMODIFIERS=@im=fcitx
   ```
   这套变量由安装器写进装后系统的 `/etc/environment`（Live 不需要输入法，不装这一套）。
2. **自启动与 profile 配置** 

### 2.3 本地化层

| 项目 | 内容 |
|---|---|
| `/etc/locale.gen` | 预生成 `zh_CN.UTF-8` |
| `/etc/locale.conf` | `LANG=zh_CN.UTF-8` |
| `/etc/vconsole.conf` | 控制台字体与键盘布局 |
| 时区 | `Asia/Shanghai` |
| `/etc/skel/` | 新用户默认的 `.bashrc`、`.xprofile` 等 |

### 2.4 网络层

**关键要求：**

> 安装完成后，**目标系统也必须继承国内镜像源**。

只在 Live 环境生效是不够的——用户装完之后第一次 `pacman -Syu` 就会退回到官方源。
落法不是「代码里写死一份源」，而是**把安装时 Live 的 mirrorlist 整份写进目标**（见 [03-项目结构](03-项目结构.md) 第 4 节）。

**网络环境变更可以自动修改最佳镜像源** 请见
[#91](https://github.com/MipLinux/MipLinux/pull/91)

### 2.5 文档层

装完后，用户在本机就能查到一份中文上手说明。

**经验判断：这比多预装一个软件更有价值。** 中文用户遇到问题的第一障碍是找不到中文资料，
一份准确的本地文档能显著降低挫败感。这份说明要跟系统一起交付，而不是让用户先去网上找。

## 第三部分 · 一致性要求

### 3.1 包清单只有一个来源

Live 环境与安装器写盘时使用的包清单**必须来自仓库里受版本控制的清单文件**，
不允许安装器在代码里另写一份「装什么包」的列表。

### 3.2 镜像源的双重生效

镜像源需要在两个地方生效：

| 位置 | 目的 |
|---|---|
| profile 的 `pacman.conf` | 构建时使用国内源拉包 |
| `airootfs/etc/pacman.d/mirrorlist` | 装后系统继承国内源 |

两者不能只做一半。
