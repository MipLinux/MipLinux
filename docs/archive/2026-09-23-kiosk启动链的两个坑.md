# 2026-09-23 · kiosk 启动链的两个坑：执行位被 mkarchiso 重置 + cage 拿不到 seat

> 阶段：线 G（启动链收尾）→ 收 #50 / #51。
> 这是一个验收项（「开机直进安装器窗口」）上**两个互不相干**的故障，
> 所以写在一篇里 —— 它们串在同一条链上，分开看会以为是同一个问题的两次反复。
>
> 1. **执行位被 mkarchiso 重置**（§二）：仓库里是 `755`，进 ISO 变 `644` → `EACCES`。
>    这是 #51 里那句「`Permission denied` 与仓库里的 `755` 对不上」的真正答案。
> 2. **`cage` 拿不到 seat**（§三）：`libseat` 两个后端都失败 → `cage` 起不来。
>    这个坑**跟执行位无关**，是补完 shebang、修完执行位之后才露出来的下一层。
>
> 两个坑都修了、ISO 重建并核对过产物，**开机自动出现窗口也实测通过了**（见 §六）；
> `#51` 验收里另外两条（`systemctl kill` 落回 TTY、`journalctl -u` 干净）还没单独跑。

---

## 一、症状（两个坑叠在同一个验收项上）

`mipl-installer.service` 一直 `activating (auto-restart)`，窗口一次都不出现：

```text
Process: 1017 ExecStart=/usr/local/bin/mipl-kiosk (code=exited, status=203/EXEC)
mipl-installer.service: Unable to locate executable '/usr/local/bin/mipl-kiosk': Permission denied
mipl-installer.service: Failed at step EXEC spawning /usr/local/bin/mipl-kiosk: Permission denied
```

外加一个看起来毫不相关的现象：**QEMU 窗口黑屏**，但 `systemctl kill mipl-installer` 之后
tty1 立刻回来（#51 里也记了这条兜底是通的）。

## 二、第一个坑：执行位被 mkarchiso 重置（`EACCES`）

`mkarchiso`（archiso 90-1）的 `_make_custom_airootfs()`：

```bash
_unshare cp -af --no-preserve=ownership,mode -- "${profile}/airootfs/." "${pacstrap_dir}"
#                    ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~ 先无条件丢掉模式
for filename in "${!file_permissions[@]}"; do        # 再只给白名单补回来
```

也就是说 **`profiledef.sh` 的 `file_permissions` 是一张白名单，不是「可选优化」**：
airootfs 里所有文件的模式先被 `--no-preserve=mode` 重置成 umask 默认（022 → 目录 755 / 文件 644），
然后**只有列在表里的路径**会被 `chmod` 回声明值。

安装器两个入口不在表里，于是进 ISO 就成了 `644`。内核 `execve` 一个没有执行位的文件返回
**EACCES**——这正是 journal 里那句 `Permission denied`。

### 为什么是黑屏

不是显卡、不是内核、不是 ISO 损坏。`mipl-installer.service` 带
`TTYReset=yes` / `TTYVHangup=yes`，而它 `Restart=on-failure` 每 3 秒重启一次：
每次失败重启都对 tty1 做一次 TTY reset，**把控制台反复清空**。看着就是黑屏。
`systemctl kill` 掉之后循环停了，tty1 自然回来。

**「黑屏」和「203/EXEC」是同一个根因的两个面**，一开始被当成两件事查了很久。

## 三、第二个坑：`cage` 拿不到 seat（libseat 两个后端都失败）

执行位修好之后，`203/EXEC` 消失了，但**窗口仍然不出现**。
这时候串口里已经能看到 `[ OK ] Started MipLinux 安装器界面.` ——
服务起来了，是它自己退出又被 `Restart=on-failure` 反复重启。

### 症状：看 journal 才看得见（串口看不到）

unit 里 `StandardOutput=journal` / `StandardError=journal`，所以 `cage` 的抱怨**不进串口**，
必须进 Live 敲 `journalctl -u mipl-installer -b`：

```text
Started MipLinux 安装器界面.
mipl-kiosk[606]: [libseat] [libseat/backend/seatd.c:64] Could not connect to socket /run/seatd.sock: No such file or directory
mipl-kiosk[606]: [libseat] [libseat/libseat.c:76] Backend 'seatd' failed to open seat, skipping
mipl-kiosk[606]: [libseat] [libseat/backend/logind.c:638] Could not get primary session for user: No data available
mipl-kiosk[606]: [libseat] [libseat/libseat.c:76] Backend 'logind' failed to open seat, skipping
mipl-kiosk[606]: [libseat] [libseat/libseat.c:79] No backend was able to open a seat
mipl-kiosk[606]: [backend/session/session.c:92] Unable to create seat: Function not implemented
mipl-kiosk[606]: [cage/cage.c:333] Unable to create the wlroots backend
mipl-installer.service: Main process exited, code=exited, status=1/FAILURE
```

**注意时间戳全是同一个 0.000 秒**（每次尝试都在同一毫秒死掉）。
日志里 `Scheduled restart job, restart counter is at N` 一级级往上爬，
看起来像「准备得很慢」，其实**每一次尝试都是瞬间必败**。

### 根因

`cage` 基于 wlroots，起 DRM 会话要经 `libseat` 拿一个 seat。`libseat` 有两个后端，现场两个都不通：

| 后端 | 为什么不通 |
|---|---|
| `seatd` | 守护进程没运行，`/run/seatd.sock` 不存在 |
| `logind` | 要调用方有**登录会话**（`primary session`）；systemd 服务没有会话 |

于是每次尝试都必然失败 —— 这是**确定性缺陷，不是竞态**。

### 为什么「切 tty / 手动敲」就出来了

在 tty 上登录过 root 之后，logind 才有一个属于该 VT 的会话，
`cage` 这时才拿得到 seat。这也解释了 `--serial console` 下怎么切都不出（时序不同）。

**排查时先被这个现象带偏过**：一度以为是「开机抢 VT 的竞态」「准备时间长」，
甚至怀疑过 `-vga virtio` 缺驱动。都不是 —— 决定性证据是那个 `0.000` 秒。

### 修法：用 `seatd-launch`

`man seatd-launch` 说得正合适：

> starts a seatd instance with a dedicated socket path, **waits for it to be ready**,
> and starts the specified command with `SEATD_SOCK` set appropriately.

它专为「不想（或不能）常驻一个 seatd 守护进程」的场景准备，而且**不依赖开机时的就绪时序**。
所以改 `installer/frontend/mipl-kiosk` 的最后一行：

```bash
exec /usr/bin/seatd-launch -- /usr/bin/cage -- /usr/local/bin/mipl-installer
```

`seatd` 本身**不用加进 `packages.x86_64`** —— 它已经由 `wlroots0.20`（cage 的依赖）
间接装进 Live 了（实测 ISO 里有 `/usr/bin/seatd` 与 `/usr/bin/seatd-launch`）。
代价是它成了硬依赖，所以那句注释里写明了：谁把 seatd 裁掉，这里会立刻起不来。

> 另一条同样可行的路是启用上游自带的 `seatd.service` —— ISO 里有这个 unit
> （`ExecStart=seatd -g seat`），做成 `multi-user.target.wants/` 软链即可，也不用加包。
> 没选它是因为要多一处 enable、还要处理「服务与守护进程谁先就绪」；
> `seatd-launch` 把这两件事一起解决了。

## 四、证据链（第一个坑：为什么断定是进 ISO 时丢的）

| 环节 | `mipl-kiosk` 的模式 |
|---|---|
| git 索引（`git ls-files -s`） | `100755` |
| 工作区 | `755` |
| `cp -a` 之后（umask 022 / 077 / 000 三档都试过） | `755` |
| 装配副本 `out/profile-staged/…` | `755` |
| **ISO 的 `airootfs.sfs`** | **`644`** ← 断在这里 |

同一张 ISO 内部的对照最能说明问题 —— **同一来源、同一目录层级，只差在表里有没有**：

```text
-rwxr-xr-x  /usr/local/bin/choose-mirror       ← 在 file_permissions 里
-rwxr-xr-x  /usr/local/bin/livecd-sound        ← 在
-rw-r--r--  …/frontend/mipl-kiosk              ← 不在 → 644
-rw-r--r--  …/frontend/mipl-installer          ← 不在 → 644
```

## 五、修法（第一个坑）

`profile/profiledef.sh` 的 `file_permissions` 加两行（表里已就地写了注释说明为什么不是可选）：

```bash
["/usr/local/lib/mipl-installer/frontend/mipl-installer"]="0:0:755"
["/usr/local/lib/mipl-installer/frontend/mipl-kiosk"]="0:0:755"
```

**声明的路径是 `frontend/` 下的真文件，不是 `/usr/local/bin/` 下那两条软链** ——
软链本身没有模式可言，起作用的是它指向的目标。

> **规矩：以后往 Live 里加任何可执行文件，`file_permissions` 必须同步加一行。**
> 漏了不会构建失败，只会开机 `203/EXEC` —— 而那个现场比构建失败难查得多
> （这次就从「软链悬空」一路查到「mkarchiso 改模式」，中间隔着一条串口日志）。

## 六、验证到哪一步了

按仓库口径分层写 —— **「窗口能画出来」和「开机自动出现窗口」是两件事，不能合并成一句「修好了」**：

**✅ 已实测 ①：执行位进 ISO 是 755 了**

加了两行之后重建一次 ISO（容器内 4 分 46 秒），解出 `airootfs.sfs` 逐条核对：

```text
-rwxr-xr-x root/root  …/frontend/mipl-installer      ← 644 → 755
-rwxr-xr-x root/root  …/frontend/mipl-kiosk          ← 644 → 755
lrwxrwxrwx root/root  /usr/local/bin/mipl-kiosk -> ../lib/mipl-installer/frontend/mipl-kiosk
```

同一张 ISO 上顺带对过：两个入口首行仍是 `#!/bin/bash` / `#!/usr/bin/env python3`；
表里原有条目**没被误伤**（`/etc/shadow` 400、`/root` 750、`.gnupg` 700、
`automated_script.sh` 755、`choose-mirror` / `Installation_guide` / `livecd-sound` 755）；
引导配置的 `archisosearchuuid` 与 ISO 上 `.uuid` 文件名一致。

**✅ 已实测 ②：界面本身画得出来**

QEMU 里手动把 kiosk 拉起来之后，全屏出现「MipLinux 安装器 / M0 · 占位界面（真界面 M2）」，
中文正常、鼠标指针在、QVBoxLayout 居中正常。这说明
**cage + Wayland + PySide6 + Noto CJK 这一整条链是通的**。

**✅ 已实测 ③：`seatd-launch` 那条修复有效 —— 开机不碰键盘，窗口自己出来**

这是 `#51` 的验收项。加 `seatd-launch` 之后重建 ISO、QEMU 开机：

- 窗口**自动出现**，不需要切 tty、也不需要手动敲命令；
- 此前那个「每次尝试都在 0.000 秒死掉、靠 `Restart=on-failure` 无限重试」的循环消失
  （§三 那段 journal 是修复前的现场）。

**⏳ 仍未实测：`#51` 验收里的另外两条**

`systemctl kill` 落回 TTY、`journalctl -u` 干净 —— 这两条还没单独跑。
验收结果写进 `docs/work/tech/04-安装逻辑与实测.md` —— 那是线 G 的 G2 产出，
**该文件目前还不存在**（见 [当日记录 §四](../work/2026-09-23.md)），所以这里只留指针。

**⏳ 另一个已知但没定位的问题：首帧慢**

窗口出来之后发现**从图形出现到界面画出来要 10 秒以上**（黑屏 + 鼠标先出现）。
已经排除 fontconfig 缓存（实测冷热缓存对建窗口耗时无影响：0.39s vs 0.38s），
真实 GPU 缺失＋`WLR_RENDERER=pixman` 软件渲染是因素之一，但量级对不上。
**根因未定，已另开 issue 记录并附量测方案**，不在本篇下结论。

> **顺带一条待验，而且差点被我写成错误结论**：
> `mipl.sh qemu` 不传 `--vga`（QEMU 默认 std/bochs），而 `mipl.sh installer`
> 在 `mipl.sh:906` 写死 `--vga virtio`。
> 实测出窗口的那次走的是前者，**但那次同时换了刚重建的 ISO**（见 §六 ✅③）——
> **两个变量一起变了，所以不能把「窗口出得来」归因给显卡**。
> 真正能确定的只有：**std/bochs 这条路是能出窗口的**（实测）；
> virtio 那条在**修好之前**的 ISO 上没出过窗口，是显卡还是当时的 seatd 问题，**未分离**。
>
> 值得单独验一次的理由：`mipl.sh --help` 里那句「`-vga virtio`（cage KMS，**std VGA 起不来**）」
> 与「std 实测能出窗口」**表面矛盾**，而那句话是 `fbaf861`（PR #49）加的 ——
> 那时入口连执行位都没有（#51），多半是当时一次失败留下的错误归因。
> 结论要么改代码注释、要么改文档，**但得先在同一个 ISO 上把两条命令各跑一次**。

## 七、排查方法（比这两个坑更值钱）

1. **怀疑「文件在不在」之前，先怀疑「模式对不对」。**
   `execve` 的失败码会分岔：目标不存在是 `ENOENT`，没有执行位是 `EACCES`，
   没有 shebang 是 `ENOEXEC` —— 而 systemd 把**三种都报成 `203/EXEC`**。
   所以必须把内核的 errno 单独逼出来：

   ```bash
   python3 -c "import os,errno
   pid=os.fork()
   if pid==0:
       try: os.execv('<路径>',['x'])
       except OSError as e: print(e.errno, errno.errorcode.get(e.errno))
   os.waitpid(pid,0)"
   ```

   对照结果：悬空软链 → `2 ENOENT`，无 shebang → `8 ENOEXEC`，无执行位 → `13 EACCES`。

2. **验「ISO 里到底是什么」不要去猜，直接读 squashfs。**

   ```bash
   xorriso -osirrox on -indev <iso> -extract /arch/x86_64/airootfs.sfs /tmp/sfs
   unsquashfs -lls /tmp/sfs | grep -E 'usr/local/(bin|lib/mipl-installer)'
   ```

   `unsquashfs -lls` 读的是 inode 里的真实模式，会**忠实**反映镜像
   （验证办法：拿 `bash` / `systemctl` 这类已知模式的文件做对照，
   它们在镜像里和宿主机上一致，只有 setuid 位会被削掉）。

3. **解包器本身也可能骗人**，所以每次都要留一组对照文件。
   这次差点把 `unsquashfs` 的 umask 行为当成镜像事实 ——
   用 `umask 000` 重解一遍才排除。

4. **报错文本指向的层，往往不是出问题的那一层**（这条与
   [M1 踩坑记录](2026-09-22-安装器M1踩坑记录.md) §4 同源）：
   `Permission denied` 听上去像权限配置问题，真凶是**构建工具主动重置了模式**。

5. **`mipl.sh` 一律要 root，但构建脚本的 dry-run 不要**：
   `MIPL_DRY_RUN=1 ./scripts/baseline-build.sh --auto` 普通用户就能跑，
   能把装配阶段整条路径打印出来 —— 排查「构建脚本引用的路径对不对」这类问题不用真的构建一遍。

6. **已经开着的 QEMU，串口可以事后接上去读 —— 不要为了看日志重开一台。**
   `mipl.sh qemu --serial console` 起的是一个 unix socket（`out/installer-serial.sock`），
   所谓「交互」只是说有客户端连上去就能收发。**所以它同时是一条只读探活通道**，
   本轮 203/EXEC 与 libseat 的现场就是这么拿到的：

   ```bash
   # 只收不发：拿 10 秒的当前屏幕内容，不改客机状态
   timeout 10 socat -u UNIX-CONNECT:out/installer-serial.sock -

   # 想交互（按仓库约定 Ctrl-] 退出）
   socat -,raw,echo=0,escape=0x0f UNIX-CONNECT:out/installer-serial.sock
   ```

   两个注意点：

   - `mipl.sh qemu` **不带 `--serial`**，那种实例没有这个 socket（本轮有一次就是这么扑空的）；
   - socket 属主是 root，普通用户连不上，要么用 `sudo`，要么这台 VM 本来就是你自己起的。

7. **串口看不到的，去 journal 里找。** unit 写的是 `StandardOutput=journal` /
   `StandardError=journal`，所以 `cage`、Qt、`libseat` 的抱怨**一个都不进串口**，
   只看串口会误判成「什么都没发生」。Live 里敲（或 `--serial console` 连上去敲）：

   ```bash
   journalctl -u mipl-installer -b --no-pager
   ```

   本轮两个坑的原始现场（`Permission denied`、libseat 那串）全部来自这里，
   串口那边只有一句绿色的 `[ OK ] Started MipLinux 安装器界面.`。

## 八、与 #50 / #51 的关系

四条断点叠在同一个验收项上，而且**互相会把对方盖住** —— 修掉一条，露出来的下一条
症状还是「窗口不出来」：

| 断点 | 表现 | 修在哪 |
|---|---|---|
| `baseline-build.sh` 断言/软链还写死 `installer/bin/` | 构建在装配阶段 die（#50） | 入口按目录定位 + `INSTALLER_ENTRY_DIR` |
| 两个入口没有 shebang | `ENOEXEC` → `203/EXEC`（#51） | 补 `#!/bin/bash`、`#!/usr/bin/env python3` |
| **执行位被 mkarchiso 重置** | `EACCES` → `203/EXEC`（#51） | §二：`file_permissions` 加两行 |
| **`cage` 拿不到 seat** | `Restart=on-failure` 无限重试（#51） | §三：`seatd-launch` |

前三条是**同一次「搬目录」**留下的；第四条跟搬目录毫无关系，是 M0 启动链自己缺的一环，
只是被前三条挡在后面一直没露头。

教训有两条：

1. **同一个症状背后可以并排站着多个独立原因。** 只修软链，errno 从 `ENOENT` 变成 `ENOEXEC`；
   只补 shebang，还会撞上 `EACCES`；把执行位修好，才轮到 seatd。
   每修一层都要**重新实测**，不能推断「这下应该好了」。
2. **「重试」会伪装成「很慢」。** seatd 那条每次都是 0.000 秒必败，
   但因为 `Restart=on-failure` 一直在重试，人看到的是「等一会儿就出来了」。
   看日志时**先看时间戳**，再决定是查竞态还是查确定性失败。
