# 2026-09-25 · tty1 落不回去：被 `Conflicts=` 停掉的 getty 没人拉回来

> 阶段：线 G（启动链收尾）→ M0 验收的最后一项。
> 症状：安装器窗口被 `kill` / `stop` / 崩掉之后，**tty1 是空白**，人要手动切 VT 才有 shell。
> 根因一句话：`Conflicts=getty@tty1.service` 停掉 getty 走的是**显式停止**，
> 而 `getty@.service` 的 `Restart=always` **对显式停止不生效** —— 没有任何东西把它拉回来。
>
> 兜底修好、去验「用 `systemctl start` 把界面叫回来」时，又撞上**第二个独立缺陷**：
> `seatd-launch` 被 SIGTERM 掉会留下 `/run/seatd.sock`，下一次 `seatd` 拒绝启动（§五）。
> 两个都堵在「安装器的退路」上，所以写在一篇里。
>
> 这一篇还要提醒的是：同一个验收项上，「机制推断」被写进了文档当成事实（两条），
> 而它们都没实测过。真正把它们推翻只花了十来分钟，用的还不是 QEMU。

---

## 一、症状与复现（2026-09-23 的 ISO，只读复现）

无头 QEMU（`-display none` + monitor socket + `--serial console`）里，从串口 shell 取证：

| 时刻 | 观察 | 证据 |
|---|---|---|
| 开机后 | 安装器在跑，`getty@tty1` 已经被停 | `mipl-installer=active`（`seatd-launch` → `cage` → `python3`）；cage `Modesetting with 1280x800`；`getty@tty1=inactive` |
| `systemctl kill mipl-installer` 之后 | 安装器**没被重启**，tty1 上什么都没起来 | `mipl-installer=inactive`、**`NRestarts=0`**、`getty@tty1=inactive`、`fgconsole` = 1、`/dev/vcs1` **全空** |

也就是说：屏幕停在 tty1，tty1 上没有任何进程在写提示符 —— 人看到的是黑屏，
只能靠手动切 tty2（`autovt@tty2` 只在**切过去的那一刻**才拉起 getty）或者串口。

`getty@tty1` 这一整轮 journal 是 **`-- No entries --`**：它在这次开机里**从来没起来过**
（`After=` + `Conflicts=` 让它一开机就被安装器顶掉）。所谓「getty autologin 保留为兜底」，
当时只是写在文档里的一句话。

## 二、两条被推翻的推断（都写在过 tech/04 里）

1. **「`systemctl kill` 之后 3–5 秒会被 `Restart=on-failure` 拉起来」** —— 错。
   实测 `NRestarts=0`。原因是 `systemctl kill` 默认发 **SIGTERM**，
   而 `systemd.service(5)` 的 `Restart=` 一节把 `SIGHUP` / `SIGINT` / `SIGTERM` / `SIGPIPE`
   明确定义成 **clean exit** —— `on-failure` 对它**根本不触发**。
   （结论：`Restart=on-failure` 从来就不是「kill 掉会自己回来」的机制。）
2. **「`systemctl stop mipl-installer` 之后 tty1 落回 `root@archiso ~ #`」**（09-23 记的 ✅）—— 记错了终端。
   当时人是在**串口** shell 里敲命令、也在串口上看到提示符；tty1 那边始终是空的。
   **教训：验收项必须写清「在哪个终端看」，否则串口的提示符和 tty1 的提示符长得一模一样。**

## 三、根因

- `systemd.unit(5)`：`Conflicts=` 是**双向**的 ——
  「starting it will stop all of them and **starting any of them will stop it**」。
  所以安装器一起来，`getty@tty1.service` 就被停掉，这是设计如此。
- `systemd.service(5)` 的 `Restart=`：
  「When the death of the process is a result of systemd operation (e.g. service stop or restart),
  the service will not be restarted.」——
  **被 `Conflicts=` 停掉属于 systemd 主动停止**，`Restart=always` 救不了它。
- 安装器这条 unit 自己也没有「我走了以后谁接管 tty1」这一步。三个缺口叠在一起，
  结果就是「tty1 变成一个没人管的黑洞」。

## 四、三种候选机制，逐个量了一遍（用户级 systemd，不用起 VM）

| 机制 | `stop` / `kill` / 崩溃 → 落回 tty1 | `systemctl restart` |
|---|---|---|
| `ExecStopPost=systemctl start getty@tty1` | ✅ 三种都行 | ❌ 把重启的启动作业抢掉（`Job ... canceled`），安装器停在 inactive |
| `OnSuccess=` / `OnFailure=` **直接**指向 `getty@tty1.service` | ✅（与上一行同因） | ❌ 更糟：偶发**两者同时 active**，一起抢 tty1 的键盘输入 |
| `OnSuccess=` / `OnFailure=` → **独立兜底单元**（延迟后查状态再决定） | ✅ | ✅ 连做 3 次都稳定（安装器 active、getty inactive） |

**为什么 `restart` 必须一起量：** `systemctl restart` 的前一半就是「停止」，
所以任何挂在「停止」上的钩子都会在重启时误触发。`ExecStopPost` 那一行还有一层：
它**跑在停止序列里面**，此刻 unit 的 `ActiveState` 必然是 `deactivating` ——
想在钩子里「查一眼状态再决定」是查不出来的，信息只能来自停止序列之外（即独立单元）。

**修法**（`profile/airootfs/etc/systemd/system/`）：

- `mipl-installer.service`：去掉 `Restart=on-failure` / `RestartSec=3`，
  加 `OnSuccess=` / `OnFailure=mipl-installer-tty.service`；
- 新增 `mipl-installer-tty.service`：`Type=oneshot`，先等 2.5 秒看安装器有没有回到 active，
  没回来才 `systemctl start getty@tty1.service`。

`Restart=` 去掉是**语义选择**，不只是实现细节：「崩了就自动再来一次」与
「崩了就把 tty1 交回用户」互斥（同时配上会互相抢作业）；而 M0 的验收要的是后者。
安装中途崩了也不该在残骸上接着装（同 [installer-roadmap](../work/installer-roadmap.md) §6 的
「失败不留半成品」）。要重开界面：`systemctl start mipl-installer`。

## 五、第二个坑：重开界面起不来（`seatd-launch` 残留的 socket）

兜底修好之后，「`systemctl start mipl-installer` 把界面叫回来」这条退路**仍然是死的**：

```text
Started MipLinux 安装器界面.
mipl-kiosk[1125]: 00:00:00.000 [ERROR] [seatd/seatd.c:162] Socket file found at socket path /run/seatd.sock, refusing to start
mipl-kiosk[1112]: seatd exited prematurely
mipl-installer.service: Main process exited, code=exited, status=1/FAILURE
```

`seatd-launch` 起的那个 seatd 用的是**写死**的 `/run/seatd.sock`：

- 实测 `SEATD_SOCK=/tmp/probe.sock seatd-launch -- …` **无效** —— seatd 还是去开 `/run/seatd.sock`；
  它也没有指定路径的选项（`seatd-launch -h` 只有 `-l` / `-h` / `-v`）。
- **正常退出会自己收掉**：`seatd-launch -- /bin/true` 之后 socket 不存在（seatd 日志里有 `seatd stopped`）。
- **被 SIGTERM 掉就不会**：`systemctl stop` / `kill` 把整个 cgroup 一发信号打死，
  清理那一步没机会跑 —— socket 留着，下一个 seatd 看到文件就拒绝启动。

判别「残留」还是「有人在用」用 `fuser`（实测：残留 → 退出码 1；活着的 seatd → 0）：

```bash
if [[ -S /run/seatd.sock ]] && ! fuser -s /run/seatd.sock 2>/dev/null; then
      rm -f /run/seatd.sock
fi
```

这句加在 `installer/frontend/mipl-kiosk` 的 `exec seatd-launch` 之前。
`fuser` 在 Live 里由 `psmisc` 提供（本来就在清单里，不用加依赖）。

> 另一条更彻底的路是启用 ISO 自带的 `seatd.service`（`ExecStart=seatd -g seat`），
> 让 seatd 常驻、生命周期交给 systemd，`mipl-kiosk` 直接 `exec cage` ——
> 那就不存在「谁来收 socket」这个问题。这次没走，是因为它要多一处 enable
> 并重排 kiosk 与 seatd 的就绪顺序，超出 M0 收口的范围。**留作后续候选。**

## 七、沉淀：这次的排查方法

1. **`systemctl --user` 就是 systemd 语义的实验台。**
   造两个互相 `Conflicts=` 的假 unit（`/bin/sleep infinity` 就够），
   `stop` / `kill` / `SIGKILL` / `restart` 四条路径各走一遍，几十秒出结论 ——
   比「重建 ISO（十几分钟）+ 起 QEMU + 人眼看窗口」快两个数量级。
   这次三个候选机制就是在用户级 systemd 上筛完的，QEMU 只用来做最终验收。
2. **实验自己会骗人，先确认钩子单元是 `loaded`。**
   第一版钩子写了 `date +%T.%3N`，`%3N` 被 systemd 当 specifier 直接报
   `bad-setting`，于是「钩子一次都没触发」被读成「机制无效」。
   `systemctl --user show -p LoadState <hook>` 一条命令就能排除。
3. **`systemctl is-active --quiet` 对 `activating` 返回 3，不是 0。**
   兜底单元里靠它判断「安装器回来了没有」，得知道这个数（实测）。
4. **`ExecStart=` 里不能出现 `%`** —— systemd 会把 `%s` / `%n` 这类当 specifier 展开
   （实测 `%s` 变成了调用者 shell 的路径 `/bin/fish`）；
   `$(...)` 才会原样交给 `sh`。
5. **`/dev/vcsN` 是「tty 上到底有没有提示符」的权威证据。**
   无头 QEMU 的 `screendump` 只看得见内核控制台（VGA 文本模式），
   cage 用 KMS 设了模式之后截出来是**纯黑**——别据此判断「窗口没出来」，
   要看 `mipl-installer` 的状态、cage 的 `Modesetting` 行，或直接读帧缓冲。
6. **串口取证要留足时间。** `socat - UNIX-CONNECT:...` 在 stdin EOF 时立刻退出，
   客机里 `sleep 6` 之类迟到的输出会被整段丢掉 —— 收尾的 sleep 必须比客机里的等待长。
7. **「兜底」和「退路」要一起验。** 兜底让 tty1 回来了，人下一步必然想「那把界面再开起来」——
   那是另一条进程链（`seatd-launch` → `cage`），有自己的失败模式（§五）。
   一条「挂了能救回来」的验收，要把「救回来之后还能不能继续干活」一起算进去。
8. **`OnSuccess=` 与 `OnFailure=` 指向同一个单元时，systemd 会记一句
   `multiple trigger source candidates for exit status propagation (…), skipping`。**
   那只是它没法决定把退出码传播给谁，与用法无关 —— 本次实测兜底照常工作，别把它当故障查。
