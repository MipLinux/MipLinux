## 已踩过的坑（执行前先看）

### 坑 1 · 复用工作目录会让改动**静默失效** ← 今天最可能踩的

`mkarchiso` 用**标记文件**保证某些步骤只跑一次。已核对 archiso 90 的源码：

```bash
_run_once() {
    if [[ ! -e "${work_dir}/${run_once_mode}.${1}" ]]; then
        "$1"
        touch "${work_dir}/${run_once_mode}.${1}"
    fi
}
```

标记写在**工作目录**里，而下面这些步骤全都挂了 `_run_once`：

- `_make_packages` —— 装包
- `_make_custom_airootfs` —— 拷 `airootfs/`
- `_build_iso_image` —— 生成 ISO 本体

**后果：用同一个 `-w` 目录重建，它不重装包、不重拷 `airootfs/`、甚至不重建 ISO。** 你会拿到一个「构建成功」的**旧产物**，然后花半天怀疑自己的配置写错了。

还有一处：`${work_dir}/build_date` 存在时，`SOURCE_DATE_EPOCH` 会沿用里面记的旧值，新产物的日期是旧的。

**规则：改完 profile 必须换工作目录，或先删掉旧的。** ✅ 9.19 已实现（A3）：`mipl build` 构建前自动清空工作目录；要故意保留用 `--keep-work`。

> **更正（9.19 实测）**：容器里的 `/tmp` 是 `systemd-nspawn` 默认覆盖上去的
> **tmpfs（内存盘）**，容器一停内容就没了；而且默认只有 10% 内存大小（本机 ≈3 GiB），
> 构建树到写 efiboot.img 时恰好撞线，报的是 `plain_io read/write: No space left
> on device` —— Issue #6「/tmp 空间不足」的真身就是这个。所以工作目录的默认值
> 已改成容器内的 `/var/tmp/mipl-work`。
>
> 9.18 那次手工构建用的是 **`/var/tmp/mkarchiso`**（容器内普通目录 → 宿主磁盘），
> 它**确实还在**：`/var/lib/machines/archbuild/var/tmp/mkarchiso`，里面的
> `base._make_packages` / `build_date` 等标记就是上面这条坑的实物证据。

### 坑 2 · 旧的 nspawn 容器没关

机器名 `archbuild` 被上一个未退出的容器占用时，报 `Mount point '.../unix-export' exists already`。

```bash
sudo machinectl poweroff archbuild
```

`mipl shell --restart` 会先关掉它。

### 坑 3 · 搬 profile 时**不要**顺手修 `pacman.conf`

看到 `Include = /etc/pacman.d/mirrorlist` 会很想改——**今天别改**。

它确实是个陷阱：已核对源码，`_make_pacman_conf` 里跑的是

```bash
pacman-conf --config "${pacman_conf}" | sed ...
```

这是在**构建容器**里解析的，读的是**容器的** `/etc/pacman.d/mirrorlist`。所以在 CachyOS 上构建会静默产出「CachyOS 源做的 ISO」。

但这是线 C 的活，而且要单独一次构建来验证。今天搬 profile 的任务是证明「新路径能用」，混进来就又分不清了。
