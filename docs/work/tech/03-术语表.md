# 术语表 · 各工具是什么、彼此什么关系

> 这篇文档解释本项目涉及的各个名词，以及它们如何组合在一起。
>
> 如果你已经熟悉 Arch 的构建流程，可以跳过。

---

## 1. 全链条总览

```
archlinux-bootstrap-*.tar.zst    ← 一堆文件（一个 Arch 系统的内容）
        │
        │  解压进一个目录
        ▼
   /var/lib/machines/archbuild/  ← 一个目录，里面是 Arch
        │
        │  systemd-nspawn 让这个目录「跑起来」
        ▼
   运行中的 Arch 容器              ← 在这里跑 mkarchiso
        │
        │  mkarchiso 读 profile
        ▼
      miplinux.iso               ← 产物
        │
        │  QEMU 模拟一台电脑来「引导」它
        ▼
     验证成功/失败                ← UEFI 是 QEMU 需要模拟的固件标准
```

**关键：这些工具没有一个是另一个的替代品，它们各占一个位置。**

---

## 2. Arch bootstrap

**是什么：** 一个压缩包，里面是一份 Arch 的完整文件系统。

文件名 `archlinux-bootstrap-x86_64.tar.zst`，约 120 MB，从 Arch 官方镜像站下载。

解压后是一个完整的目录树：

```
archbuild/
├── bin/  etc/  usr/  var/  lib/
├── pacman（Arch 的包管理器）
└── ...
```

**它不能自己做任何事**——就是一堆躺在硬盘上的文件。

**类比：** 像一块装好系统的硬盘分区，内容齐全，但没有运行。

**为什么需要它：** Arch 不像 Fedora/Debian 提供一个空壳安装器。官方给的「从零开始」的起点就是这个 tarball，它以 `bootstrap_packages`（`base` + `arch-install-scripts`）为准打出。

---

## 3. systemd-nspawn 与容器

**这里有一组容易混淆的概念叠在了一起：**

> `systemd-nspawn` 是**容器运行工具**，「容器」是它运行出来的**东西**，bootstrap 是喂给容器的**内容**。

| 角色 | 是什么 | 类比 |
|---|---|---|
| **bootstrap** | 一堆文件 | 食材 |
| **systemd-nspawn** | 一个程序 | 锅 |
| **容器** | nspawn 跑起来后的运行环境 | 锅里正在煮的东西 |

完整表述：

```
用 systemd-nspawn（工具）
  把 /var/lib/machines/archbuild/（bootstrap 解压出的目录）
  跑成一个容器（运行中的环境）
```

没有 bootstrap，nspawn 无米下锅；没有 nspawn，bootstrap 只是一堆静态文件。

### 为什么需要容器这一层

因为要在容器里**运行 `mkarchiso`**，而它需要：

- `pacman` 能正常工作
- 能联网下载包
- 能创建挂载点、切换根目录

这些都需要一个**正在运行的 Linux 用户空间**，不是一堆静态文件。

### 为什么不直接在宿主机上跑

```
直接在 CachyOS 上跑 mkarchiso
  → 会用到 CachyOS 的 /etc/pacman.d/mirrorlist
  → ISO 变成用 CachyOS 源做的

在容器里跑
  → 容器内是纯 Arch，宿主机是 CachyOS 或 Arch
  → 产物干净，且两人一致
```

详细机制见 [knowledge/02-环境与工具链.md](../../knowledge/02-环境与工具链.md) 第 3.1 节。

## 4. releng

**是什么：** `archiso` 包自带的一份**参考 profile**。

`releng` = **rel**ease **eng**ineering（发布工程）。

它是**官方 Arch 安装 ISO 自己的配置**——你在 archlinux.org 下载的那个 ISO，就是用这份 profile 构建出来的。

内容：

```
/usr/share/archiso/configs/releng/
├── profiledef.sh          ← 身份定义
├── packages.x86_64        ← 129 个包
├── pacman.conf
├── airootfs/              ← 叠加文件
└── efiboot/  syslinux/  grub/
```

### 为什么基线构建用它

因为它是一份**已经被全世界验证过能工作的配置**。

```
用 releng 构建成功 → 说明工具链没问题
                   → 之后 ISO 起不来，一定是你改的东西导致的

跳过 releng 直接改 → 第一次失败时分不清是环境问题还是配置问题
```

`archiso` 包另有 `baseline`（更小的最小配置，不含引导器），本项目不使用。

## 5. QEMU

**是什么：** 虚拟机软件。它模拟一整台电脑（含固件、CPU、磁盘、网卡），让操作系统以为自己在真实硬件上运行。

### 为什么不能省掉它

> **产物是「可引导介质」。验证它唯一的方法就是「引导」它。**
>
> **容器做不到这件事。**

容器是**共享宿主机内核、直接运行目录里的 systemd**，它没有「引导」这个概念。把 ISO 丢进 nspawn，它什么也做不了。

| | 容器（nspawn） | 虚拟机（QEMU） |
|---|---|---|
| 内核 | 用宿主机的 | 自己引导一个 |
| 里面有 systemd 在跑吗 | 有 | 有 |
| **能「引导」一块磁盘吗** | **❌ 不能** | **✅ 能** |
| 能启动 ISO 吗 | 不能 | 能 |
| 用途 | **构建** | **测试** |

两者都有 systemd、都能跑程序，**区别就在于「引导」这一步虚拟机有、容器没有**。

### 分工

```
nspawn  → 构建（需要 Arch 环境、需要 pacman）
QEMU    → 测试（需要引导一块磁盘）
```

测试时 QEMU **跑在宿主机上**，不在容器里。

## 6. UEFI 与 OVMF

### 为什么会有 UEFI 这个概念

因为现代电脑的固件标准是 UEFI，不是老式 BIOS，**两者的引导机制完全不同**。

发行版必须同时照顾两种，所以 ISO 里有两套引导配置：

| 固件 | ISO 里的配置目录 | 引导器 |
|---|---|---|
| **BIOS**（老式） | `syslinux/` | syslinux |
| **UEFI**（现代） | `efiboot/` | systemd-boot |

### 为什么测试时必须显式指定

QEMU 默认模拟老式 BIOS。不管它，就只测了 BIOS 路径——**而 UEFI 路径恰恰更容易出错**（EFI 分区、`.efi` 文件路径、NVRAM 引导项都是 UEFI 独有的复杂点）。

测试命令里这两行就是「请模拟 UEFI」：

```bash
-drive if=pflash,format=raw,readonly=on -file=/usr/share/edk2/x64/OVMF_CODE.4m.fd
-drive if=pflash,format=raw             -file=./OVMF_VARS.fd
```

### OVMF 是什么

**OVMF 是 QEMU 使用的 UEFI 固件实现**，来自 Intel 的 EDK II 项目，由 `edk2-ovmf` 包提供。

分两个文件：

| 文件 | 作用 | 读写 |
|---|---|---|
| `OVMF_CODE.4m.fd` | 固件程序本体 | 只读 |
| `OVMF_VARS.4m.fd` | **UEFI 变量存储**（NVRAM） | 可写 |

> **每个测试用例都要复制一份新的 `OVMF_VARS.fd`。**
>
> 引导过的系统会把自己的引导项写进 NVRAM。反复用同一份变量文件，上一次测试留下的引导项会影响下一次——表现为「上次明明能启动，这次不行了」，极难排查。

## 7. mkarchiso

**是什么：** `archiso` 包里的构建脚本，装在 `/usr/bin/mkarchiso`。**就是一个 bash 脚本。**

它做的事：

```
1. 读 profiledef.sh
2. 读 profile/pacman.conf（在【宿主机】上解析 Include）← 陷阱
3. pacstrap 一个空目录，按 packages.x86_64 装包
4. 复制 profile/airootfs/ 进去
5. 按 file_permissions 重设权限
6. 运行 mkinitcpio 生成 initramfs
7. 清理
8. mksquashfs 压成 airootfs.sfs
9. xorriso 组装成 .iso
```

**第 3 步就是「装一个完整的 Arch 系统」**，这是理解它的关键。

**为什么必须在 Arch 上跑：** 第 3 步需要 `pacman`/`pacstrap`，第 6 步需要 `mkinitcpio`——这两个在 Fedora 上不存在，也没有等价替代。这是使用容器的唯一原因。

## 8. squashfs 与 Live 环境

**squashfs 是只读的压缩文件系统。** Live 环境的整个根目录被压成 `airootfs.sfs`。

启动时：

```
ISO 里的 airootfs.sfs（只读、压缩）
        │
        │  挂载
        ▼
   ┌─────────────────┐
   │ overlay 可写层   │  ← 写在内存里
   ├─────────────────┤
   │ squashfs 只读层  │  ← 来自 ISO
   └─────────────────┘
```

**结论：** Live 环境的任何修改都只在内存里，**重启全部还原**。这就是为什么安装器必须把东西写到目标磁盘，而不是就地配置。

## 9. 一页速查

| 名词 | 一句话 | 用在哪个环节 |
|---|---|---|
| **Arch bootstrap** | 一包 Arch 文件系统 | 构建环境的原料 |
| **systemd-nspawn** | 把目录跑成容器的工具 | 构建 |
| **容器** | 运行中的纯 Arch 环境 | 构建 |
| **releng** | 官方参考 profile | 构建的起点 |
| **mkarchiso** | 构建脚本 | 构建 |
| **profile** | 你的配置文件目录 | 构建的输入 |
| **squashfs** | 只读压缩文件系统 | Live 环境的根 |
| **QEMU** | 虚拟机 | 测试 |
| **OVMF** | QEMU 的 UEFI 固件 | 测试（UEFI 路径） |
