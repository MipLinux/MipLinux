# AGENTS.md — docs/ 文档标准

这个项目的文档是技术资产。文档写错的代价比代码更高 —— 维护者在两台不同的机器上照着它操作。
本文只写 `docs/` 特有的规矩；通用红线在[根文件](../AGENTS.md)。

## 三层的职责

| 层 | 放什么 | 不许出现什么 |
|---|---|---|
| `knowledge/` | **已确定的结论**，给新手读 | 「待解决」「以后再说」、修订痕迹、已出局的候选 |
| `work/` | 待执行与正在执行的工作 | 已经定案的结论（该进 `knowledge/`） |
| `knowledge/06-待定事项.md` | **还没定的问题**，编号 P | 已定案的结论（该写回 README 的 D 表） |

定案的流向是单向的：`06` 的 P 表（背景 / 候选 / 影响面）→ 定案后结论写回 `README.md` 的 D 表 → `06` 保留推导过程与排除表。
`knowledge/` 是**当前状态**，不记「什么时候改过」—— 那是 git 的事。

## 决策编号

- **不擅自新增或修改 D 编号。** D1–D14 是决策史，改它等于改写项目既有的约束。
- `06` 末尾的排除表是「已否决」档案：不重复讨论，也不擅自移出。
- 新决策先以 P 编号进 `06` 走推导，定案后才升 D。

## 写作约定

- **提到人时用角色称呼**（维护者、贡献者），不写「朋友」「某某的分支」；人数会变，别把人数写进流程描述。
- **引用已有结论时给链接，不要重述** —— 重述会产生第二份会漂移的真相。
- `work/` 的当日记录按 `YYYY-MM-DD.md` 命名；可复现的操作步骤放 `work/tech/`。
- 每一步的实测结果写进 `work/tech/`，**不要把「跑过一次」当成「验过」**。
- 文档改动同样要在 PR 里写验证方式；纯文档改动可整段写 `N/A`，不留空。
