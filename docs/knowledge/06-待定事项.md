## P5 · 交付桌面：niri / Hyprland — 🚧 未实测

**已定的方向：** 交付桌面走 WM 路线，不做完整桌面环境（DE）。DE 不是永久排除，而是排在 WM 版本之后 ——
否决理由见文末排除表。

**候选只有两个：**

| 合成器 | 包 | 特点 |
|---|---|---|
| niri | `niri` | 滚动平铺（scrollable tiling），配置用 KDL |
| Hyprland | `hyprland` | 动态平铺，配置用 hyprlang，社区与插件生态更大 |

**要比的维度（目前全部未实测）：**

| 维度 | 为什么重要 |
|---|---|
| NVIDIA + Wayland 稳定性 | **硬约束** —— D4 / D8 整条驱动线的前提 |
| 中文翻译完备度 | 「中文友好」是核心卖点 |
| fcitx5 集成 | Wayland 下输入法依赖 `text-input` 协议与环境变量，各合成器支持程度不同 |
| 配置与上手成本 | 目标用户是从 Windows 来的中文用户 |
| 与极简 Live 的配合 | Live 的 kiosk 会话（D12 / D14）可能与用户桌面复用同一个合成器 |
| NVIDIA 专有驱动的已知坑 | `nvidia_drm.modeset`、显式同步等在各合成器下表现不同 |

**怎么定案：** 别在文档里比，装一次比 —— 同一张 ISO 装到 `out/target.qcow2`，再各上真机跑一轮，
只测三件事：**驱动能亮、输入法能打字、中文能显示**；谁先跑通谁就是基线。
试跑步骤、判据与两轮（基线 / 强制 N 卡）的区分见 [tech/05](../work/tech/05-装后系统验证.md) 第 2.3 节。

**与其它工作的关系：** P5 不阻塞「逻辑先于外壳」（D14 的第一步是纯脚本），
但阻塞中文线的输入法集成与品牌化（壁纸、主题、图标）。

## P10 · 包清单的组织方式 — 🚧 方向已明，未定案

**问题：D6 定了「同一份包清单供 Live 与装后系统共用」，而 D11（在线安装）与 D12（极简 kiosk）之后，两个环境要的包不是一个集合。**

| 环境 | 需要 | 不需要 |
|---|---|---|
| **Live**（极简，清单写死） | 安装器及其依赖、联网配置、CJK 字体、分区与装包工具、N 卡驱动 | WM / 桌面、输入法、音频、浏览器 |
| **装后系统**（更大） | 装后基础清单（能启动、能升级的最小集）+ 用户在安装器里勾选的应用 | 安装器本身及其依赖（`cage` / `electron44` 等 Live 专属件） |

**为什么不能就这么放着：** D6 的理由（防止「Live 里能用、装完不能用」）依然成立 ——
它是一条**一致性**要求，不是「只能有一个文件」的要求。真正的风险是两份清单各写各的，
最后变成「Live 能跑、装后系统缺包」。

**候选：**

| 方案 | 说明 | 代价 |
|---|---|---|
| A. 两份清单 + 一套规则 | 都进 git：**Live 精简清单**（写死）+ **装后基础清单** + **应用目录**（用户在安装器里勾选的应用清单）；D6 重述为「唯一来源、禁止手写第二份清单」；三者关系写进 [03-项目结构.md](03-项目结构.md) 第 7.1 节 | 要明确「基础 / 应用 / Live 独有」规则与勾选界面，并让检查脚本能验 |
| B. 仍只维护一份 | Live 也装全量包，只是界面极简 | ISO 体积回到全量，与 D11 / D12 的初衷相抵 |
| C. 一份全量 + 一份差异清单 | 由脚本派生 Live 清单 | 多一层派生逻辑，排查「这个包是谁带进来的」变难 |

**已经明确的方向（未定案）：**

1. 两份清单各司其职：**Live 精简**（`profile/packages.x86_64` 继续按极简形态瘦身 ——
   releng 继承的救援类包如 `clonezilla`、`testdisk`、`memtest86+` 在 Live 里没有用途），**装后更大**；
2. **装后系统装哪些应用不写死**：装后基础清单 + 用户在安装器里勾选的应用，勾选结果由装包阶段的脚本安装；
3. **基础集合两边一致**；应用目录里的包两边都不默认装，只有用户勾选才装；
4. 中文三件套与 N 卡驱动已在装后基础清单里 —— 装后系统要能显示中文，`fcitx` 环境变量与 CJK 字体
   fallback 也靠这些包才生效。

在线安装下，每多一个默认包都要在安装时现拉一次 —— 基础清单的边界因此也是安装时长的边界。

**现状：** 两份清单事实存在 —— Live 清单 `profile/packages.x86_64`，装后基础清单
`installer/backend/mipl_installer/data/target-packages.x86_64`（M1 临时，定案后改指向唯一来源并删除该文件）。
安装器的清单读取已经拒绝把 Live 清单当装后清单用：墙立起来了，缺的是规则。

**定案时要一并拍：** 装后基础清单的落位（留在 `data/` 还是进 `profile/`）、应用目录的形态、
基础 / 应用 / Live 独有的边界（如 `nvidia-open` 是否默认勾选）、D6 的重述措辞 ——
它决定清单读取与勾选界面的改动面。

**倾向：** A —— 只有它同时保住 D11 / D12（Live 极简）与 D6 的初衷（两边一致），
并且「装后装什么应用」由用户在安装器里决定，不写死在任何一份清单里。

**影响面：**

| 候选 | 涉及文件 | 检查脚本怎么验 | 主要代价 |
|---|---|---|---|
| A | 装后基础清单落位、应用目录形态、[03-项目结构](03-项目结构.md) 7.1、[roadmap](../work/installer-roadmap.md) M3 行、清单读取的拒绝逻辑改指向 | 断言「仓库里只有 Live 清单 + 装后基础清单 + 应用目录 + 规则文件」；断言基础集合两边一致；断言代码里没有手写包名 | 要定义基础 / 应用 / 独有规则与勾选界面，规则本身也要防漂移 |
| B | 仅 `profile/packages.x86_64`；删清单读取的拒绝逻辑 | 无需新增，最省 | ISO 体积回全量、Live 装一堆用不上的（WM / 输入法），与 D11 / D12 相抵 |
| C | 新增全量清单 + 派生脚本；Live 清单变生成产物 | 断言 Live = 全量 − 差异（可再生成比对） | 多一层派生，排查「谁带进来的包」变难 |

## P11 · 第三方仓库政策（`archlinuxcn`） — 🚧 未定

**问题：两份 `pacman.conf` 都启用了 `[archlinuxcn]`，且都不校验签名** ——
构建用的 `profile/pacman.conf`，以及 Live 与装后系统继承的 `profile/airootfs/etc/pacman.conf`
（两者都写着 `SigLevel = Optional TrustAll`）。内部构建无所谓，对外发布不是。

D10 定了对外发布：用户装完的系统里会带着一个不校验签名的第三方源。
而**装后系统的 `pacman.conf` 由安装器从 Live 配置写入目标**（D14），所以安装器必须先知道写什么。

**三个候选：**

| 方案 | 说明 | 代价 |
|---|---|---|
| A. 收紧到签名校验 | 装 `archlinuxcn-keyring`，`SigLevel` 改为 `Required DatabaseOptional` | 装后系统多一个 keyring 包；首次 `pacman -Sy` 前必须已导入 key |
| B. 默认不启用，安装器里可选 | 装后系统默认只有官方源；要用的用户在安装器里勾选 | 安装器多一个开关；勾选后仍要处理 keyring |
| C. 保持现状 | 一行不改 | 对外发布时是明确的安全折扣，必须写进发布说明 |

**红线：** 不新增第三方仓库、不改 `SigLevel`（[根 AGENTS.md](../../AGENTS.md)）——
这条只能由维护者定，定案前谁都不动这两份文件。

**何时必须定：** M4（联网与镜像）之前 —— 见 [installer-roadmap.md](../work/installer-roadmap.md) 第 8 节。

## P12 · 时区审定规则的 D 表登记 — 🚧 待登记

**规则已裁（2026-10-02 裁决 + 2026-10-06 收口），只差 D 表登记 —— 新增 D 编号要维护者点头；
登记之前，本节的规则是唯一出处。**

**要回答的问题：** 时区选择需要一份候选名单，而 tzdata 里的时区名**本身带政治表述**
（同一片地方的不同叫法、有争议地区的归属写法）。把 `list-timezones` 原样倒出来，
等于由 MipLinux 来呈现这些表述；自己撰写中文显示名，等于把表述责任更直接地揽到自己身上。

**已裁的两条（不在候选里）：**

| 决定 | 理由 |
|---|---|
| **不放世界地图** | 地图必须画边界，而地图与地名在不同司法辖区各有规范与审批要求 —— 这件事**改代码规避不了**，只能不做。时区页因此只有「筛选框 + 列表」 |
| **名单取运行系统的 `zone1970.tab`** | `list-timezones` 混着同义树与历史名；`zone1970.tab` 只留一地的规范名 |

**显示规则：**

| 情形 | 显示 | 为什么 |
|---|---|---|
| 在**已过审的名表**里（`renderer/i18n/*.json` 里键名为 `timezone.name.<IANA>` 的那些） | `中国标准时间（UTC+08:00）` | 常见时区一张小表，名字改动逐次过审 |
| 表外 | `Europe/Amsterdam（UTC+01:00）` —— **照实显示 IANA id** | 名单外不撰写任何表述，只呈现 tzdata 自己的标识符；每一行都不同、可搜索 |

两种情形走**同一条已过审的模板** `timezone.display`（`%1（UTC%2）`），所以没有新增需要过审的人话。

**否掉的读法（记下来免得再讨论）：** 表外只显示 `UTC+01:00` 并按偏移去重。
它看着更中性，实际有两个后果：① 表外的时区会塌成二十来行一模一样的字，人找不到自己那座城市；
② **偏移不是时区** —— `Europe/Amsterdam` 与 `Africa/Lagos` 现在都是 +01:00，夏天却不是一个时区，
去重留下的「代表」会让用户选到一个**某季节会变成另一个时区**的值。

**排除项：** 只给偏移整体不用；不做按偏移合并；不给表外的时区编中文名。

**落地位置：** `options.timezones()` 出名单、`options.zone_offset()` 出偏移、`queries.timezones()` 出口、
`renderer/js/tz-names.js` 拼装与去重（只收敛同名等价簇）。

## 附 B · 已明确排除的方案

记录已否决的选项，避免重复讨论。

| 方案 | 否决理由 |
|---|---|
| fork CachyOS-Live-ISO | 绑定他人仓库结构，与项目目标冲突 |
| 使用 CachyOS 内核 | 需要挂载外部仓库，与「不依赖 CachyOS」的目标矛盾 |
| 使用 DKMS 作为 Live 环境方案 | squashfs 只读，Live 中编译占用内存和时间 |
| 完全从零编写安装器的分区逻辑 | 无损 resize 等操作的缺陷会造成数据丢失，风险不可接受 |
| 在宿主机直接运行 `mkarchiso` | 会静默引入宿主发行版的软件源 |
| 在 systemd-nspawn 中测试 ISO | nspawn 不具备「引导」能力 |
| 使用 stage3 / bootstrap tarball 作为交付物 | 不是可引导介质，无法满足「插上 U 盘就能装」 |
| **离线全量安装**（P3） | ISO 3–5 GB；要处理包缓存、`CacheDir`、压缩策略；而这些投入与「国内源本来就要做成默认」这一既有目标重复。在线安装的体积与迭代速度更划算 |
| **全功能桌面的 Live 环境**（P4） | ISO 更大、开机更慢，与「开机即装、路径最短」冲突；救援用途改由专门的救援介质承担 |
| **完整桌面环境（KDE Plasma 等）作为交付桌面**（P5） | 已确定 WM 路线。不做「先 Plasma、以后再换 WM」的两步走 —— 那等于把中文线做两遍。**做完 WM 版本之前不考虑 DE** |
| **Calamares 作为安装器**（P6） | 本体在 AUR，采用它就得自己接手维护；也避免把分区能力交给一个我们无法修的第三方组件 |
| **安装器后端用 Rust / Go**（P6） | 静态二进制要自建仓库分发，撞 D5 与 D10 的发布成本；而 Python 已经在 Live 里（`reflector` 依赖它）—— 换语言没有收益 |
| **把安装器源码放进独立仓库**（P6） | ISO 构建要跨仓库取源码，破坏「产物 ⇄ commit 一一对应」；触发迁出的条件写在 [installer-roadmap.md](../work/installer-roadmap.md) |
| **v0.1 用 C++/Qt6 + kpmcore 做分区**（P6） | 要编译、迭代慢；kpmcore 的强项（缩小已有分区）v0.1 用不到 —— 留到双系统里程碑再评估 |
| **语义版号替代产物名里的日期**（P9） | 滚动发行版里同一天重建的产物都不同，日期才是真实指纹；语义号只用于对外沟通进度 |
| **Qt Quick/QML 前端**（P6 / D14） | 书写成本过高：QML 语言本身、`qmldir` 注册顺序、`retranslate()` 语义、离屏探针各有自己的坑；这条线的价值在「界面能写、能验」，不在「用 QML」 |
| **GTK4 + libadwaita + WebKitGTK 前端**（P6 / D14 的对照） | 同样是 HTML/CSS/JS，依赖闭包只比 Electron 省一点，却要多装一倍以上的包；WebKit 的调试与生态也不如 Chromium |
| **把 Electron 运行时与应用一起打包**（P6 / D14 的对照） | 每个应用各带一份 Chromium：仓库与 ISO 双双变大，而本项目不做跨平台分发，打包器的收益为零 |
