# 05 · 测试方法

> 这篇文档说明如何验证 ISO 和安装结果，以及哪些东西必须在哪里测。

---

## 1. 核心原则

> **安装器（以及整个 ISO）直到「它装出来的系统能启动」之前，都不算被测过。**

最常见的新手错误是测到「安装器提示成功」就收工。真正的缺陷全部出现在重启之后。

---

## 2. 三个测试层次

| 层次 | 工具 | 迭代速度 | 能测什么 |
|---|---|---|---|
| 静态检查 | `mount` / `guestmount` | 秒级 | 文件是否存在、权限、配置内容 |
| 完整启动 | QEMU + KVM | ~30 秒 | 引导、安装、装后系统启动 |
| 终验 | 真机 | 5 分钟以上 | NVIDIA 驱动、双系统、畸形硬件 |

**日常开发用前两层，第三层只在版本稳定后使用。**

---

## 3. 准备测试环境

### 3.1 安装依赖

```bash
# Arch
sudo pacman -S edk2-ovmf qemu-desktop libguestfs

# Fedora
sudo dnf install edk2-ovmf qemu-kvm libguestfs-tools
```

### 3.2 准备测试资产

```bash
# 空的目标虚拟盘 —— A5 起走脚本，别手抄（脚本会顺带告诉你下一步敲什么）
sudo ./scripts/mipl.sh target              # → out/target.qcow2（40G 虚拟）

# UEFI 变量副本不用手动 cp，mipl qemu 会按用例处理好
```

> **`OVMF_VARS.fd` 必须每个测试用例单独复制一份。**
> UEFI 变量会被写入（引导项会留在 NVRAM 里），共用一份会导致后续测试结果不可信。这种污染很隐蔽——表现为「上次明明能引导，这次不行了」。
>
> **A5 起这条规则有两种执行方式，脚本已经替你分好：**
>
> | 用例 | 变量文件 | 行为 |
> |---|---|---|
> | 反复引导**同一个 ISO** | `out/OVMF_VARS.fd` | 每次 `mipl qemu` 都**刷新**（保持「干净变量」） |
> | **装好系统的盘** | `out/<盘名>.vars.fd`（如 `out/target.vars.fd`） | 跟着盘走、**保留** —— 装完重启进新系统靠的就是它 |
>
> 两份互不干扰：测 ISO 不会把装好系统的引导项刷掉。要单独清空某一份：`--fresh-vars`。

## 4. QEMU 启动命令

**用脚本，别手抄**（A5 起）：

```bash
sudo ./scripts/mipl.sh qemu --disk target.qcow2            # 装：ISO 优先 + 挂盘
sudo ./scripts/mipl.sh qemu --disk target.qcow2 --boot c   # 装完：不挂 ISO，从盘启动
```

下面这条是脚本替你拼出来的东西，留在这里是为了**出问题时能对照**：

```bash
qemu-system-x86_64 -enable-kvm -m 4096 \
  -drive if=pflash,format=raw,readonly=on \
    -file=/usr/share/edk2/x64/OVMF_CODE.4m.fd \
  -drive if=pflash,format=raw \
    -file=./OVMF_VARS.fd \
  -drive file=target.qcow2,if=virtio,format=qcow2 \
  -cdrom out/miplinux-*.iso \
  -boot order=d \
  -netdev user,id=n0 -device virtio-net,netdev=n0
```

参数说明：

| 参数 | 作用 |
|---|---|
| `-enable-kvm` | 硬件加速，本机 `/dev/kvm` 可用 |
| 两个 `-drive if=pflash` | UEFI 固件（只读）与变量存储（可写） |
| `-drive file=target.qcow2` | 目标磁盘，`virtio` 性能更好 |
| `-cdrom` | 待测 ISO |
| `-boot order=d` | 优先从光驱启动 |
| `-netdev user` | 用户模式网络，安装器可访问外网 |

**方便的话也可以用 archiso 自带的 `run_archiso` 脚本**，它封装了常用参数：

```bash
run_archiso -u -i out/miplinux-*.iso    # -u 表示 UEFI
```

## 5. 六个必须验证的检查点

按顺序执行，任一步失败就停下排查。

| # | 检查内容 | 失败意味着 |
|---|---|---|
| 1 | ISO 启动，进入 Live 环境 | 引导配置错误，或包缺失 |
| 2 | 安装器界面自动出现（不要求登录，也不要求手动启动） | 自动登录或会话自启动配置错误 |
| 3 | 安装器可操作：认得出磁盘、配得上网络 | 权限不足、依赖缺失，或网络栈配置错误 |
| 4 | **从目标盘重启，系统能启动** | ← **最关键，最常被跳过** |
| 5 | 装后系统内：用户、locale、输入法、字体正确 | 后置配置脚本未生效 |
| 6 | **装后系统能正常滚动升级**（`pacman -Syu`） | 仓库、密钥或镜像源配置错误 |

### 关于检查点 2 和 3

Live 环境是安装器的载体：开机自动登录、自动起安装器，路径上没有别的环节。
所以这两条是同一件事的两面 —— **安装器要能自己出现在屏幕上（2），并且真的能用（3）**。

检查点 3 里的「配得上网络」是在线安装带来的硬要求：装系统时要能从仓库拉包。
QEMU 用用户模式网络（第 4 节的 `-netdev user`）时默认就能出网；真机上则要看 Live 能不能
连上 Wi-Fi —— Live 的联网后端是 NetworkManager（`nmcli`）。

### 关于检查点 6

这一条值得单独强调。自制发行版的典型长期故障是：

> 能装、能用，但用户第一次系统升级就崩溃。

常见原因：

- `pacman-key --init` 和 `--populate archlinux` 未在目标系统执行
- 目标系统的 `mirrorlist` 指向错误或不可用的地址
- 混入了构建机的配置

**必须在每次发版前手工验证这一条。**

## 6. 静态检查（不开机）

调配置时，先挂载检查比启动快一个数量级。

### 6.1 检查 ISO 内容

```bash
sudo mount -o loop,ro out/miplinux-*.iso /mnt
```

### 6.2 检查装完的虚拟盘

```bash
sudo guestmount -a out/target.qcow2 -i /mnt
```

可以直接确认：

- `/etc/passwd`、`/etc/group` —— 用户是否正确创建
- `/etc/locale.conf` —— 语言设置
- `/etc/pacman.d/mirrorlist` —— **镜像源是否已继承**
- `/usr/lib/modprobe.d/` —— NVIDIA 相关配置是否存在
- `/etc/fonts/local.conf` —— 字体 fallback

检查完记得 `sudo guestunmount /mnt`。

## 7. QEMU 与真机的分工

| 测试项 | QEMU | 真机 |
|---|---|---|
| 包是否正确安装 | ✅ | — |
| 引导流程 | ✅ | — |
| 安装器界面与流程 | ✅ | — |
| 分区逻辑 | ✅ | — |
| 装后系统启动 | ✅ | — |
| **NVIDIA 驱动加载** | ❌ | ✅ **唯一手段** |
| **双系统 / 已有 ESP** | ❌ | ✅ **唯一手段** |
| **EFI 固件差异** | ❌ | ✅ （某些主板行为不同） |
| **真实磁盘与 NVMe** | ❌ | ✅ |

### 分工建议

- **90% 的开发循环在 QEMU 中完成**
- **版本稳定后再上真机**，重点验证 NVIDIA 驱动和双系统场景

## 8. 安全规则

> **分区代码的缺陷会摧毁数据。**
>
> **第一版分区逻辑的测试，必须在虚拟磁盘上进行，绝不接触真实硬盘。**

具体建议：

1. 日常开发全部在 `target.qcow2` 上测试
2. 真机测试使用**独立的硬盘或旧机器**，不要在日常工作机上试验分区逻辑
3. **第一版不要实现「调整已有分区大小」** —— 无损 resize 要做到不出错，得靠 `kpmcore` 这类久经使用的分区库；自己实现极易造成数据丢失

---

## 9. 关于自动化

QEMU 支持 QMP 接口，可以通过脚本模拟按键、截图、抓取串口输出，实现自动回归测试。

**但当前阶段不需要过早投入。**

原因：

- 逻辑尚未稳定，自动化脚本会频繁失效
- 手工循环只需 30 秒，负担不大
- 值得自动化的只有检查点 4–6，等流程固定后再说

## 10. 构建产物的一致性验证

由于维护者的宿主机发行版不同（CachyOS 与 Arch），需要确保各自构建的结果一致。

**验证方法：**

将构建放进 systemd-nspawn 的纯 Arch 容器中，且 profile 的 `pacman.conf` 不使用 `Include`（详见 [02-环境与工具链.md](02-环境与工具链.md) 第 3.1 节与 [03-项目结构.md](03-项目结构.md) 第 4 节）。

**验证步骤：**

1. 各自在同一 commit 上构建一次
2. 对比产物的 SHA256

> 注意：由于包版本是滚动的，**不同日期构建的产物不可能一致**，这是正常的。
> 一致性验证应在**同一天**、使用**同一份镜像快照**的前提下进行。

## 11. 安装器的端到端验证

安装器**在它装出来的系统能启动之前都不算被测过**（第 1 节）。用现成的命令就能跑完整条链：

```bash
sudo ./scripts/mipl.sh target --force                       # 1. 建一块空白目标盘
sudo ./scripts/mipl.sh qemu --disk target.qcow2             # 2. 进 Live，跑安装
sudo ./scripts/mipl.sh qemu --disk target.qcow2 --boot c    # 3. 检查点 4：从盘启动
```

然后逐条确认：

| 验什么 | 怎么验 |
|---|---|
| 引导项写对了 | `--boot c` 能进系统；盘上没引导项时脚本会明确报 `no bootable device`，不会悄悄回到 Live |
| 分区与文件系统 | `guestmount -a out/target.qcow2 -i /mnt`，看 `/etc/fstab` 里的 UUID 与 `lsblk` 是否对得上（第 6.2 节） |
| 继承了国内源 | `/etc/pacman.d/mirrorlist` 指向国内镜像，而不是官方源 |
| 内核参数落地 | loader entry 的 `options` 里有 `nvidia_drm.modeset=1` |
| 能滚动升级 | 装后系统里 `pacman -Syu`（检查点 6） |

**全过程只在 `out/target.qcow2` 上做**（第 8 节）。真机只用于 QEMU 测不了的部分：
NVIDIA 驱动、已有分区与双系统、EFI 固件差异。
