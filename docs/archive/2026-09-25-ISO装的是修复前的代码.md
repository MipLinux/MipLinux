# 2026-09-25 · 旧 ISO 装的是修复前的代码：合并验证轮白跑一整圈

> 阶段：线 H 装后系统验证（[tech/05](../work/tech/05-装后系统验证.md) §3 合并验证轮）。
> 症状：一整圈验收的判据白跑 —— 装出来的系统跑的是修复前的代码，结果不能作数。
> 根因一句话：QEMU 里跑的是 **ISO 里打包进去的代码**，不是工作树；17:02 构建的 ISO
> 比 17:59 落进 `configure.py` 的修复旧，判据按「修复后」的预期跑，验的全是旧代码。

---

## 一、时间线

| 时刻 | 事件 |
|---|---|
| 17:02 | `out/miplinux-2026.09.25-x86_64.iso` 构建完成 |
| 17:59 | `installer/backend/mipl_installer/configure.py` 的修复落到工作树 |
| 之后 | 合并验证轮用 17:02 的 ISO 跑完整条链 —— 装的是 17:59 修复**前**的代码 |

## 二、症状

判据结果对不上刚修完的代码，一整圈 QEMU 白跑 —— 直到对过时间戳才发现，
这一圈验证的对象根本不是当前代码。

## 三、根因

安装器跑在 ISO 里：构建把仓库代码打包进 airootfs 的时机是 `build`，不是 `qemu`。
工作树改了代码 ≠ ISO 变了 —— **代码修复之后必须重建 ISO**，验收才拿得到新代码。

## 四、怎么发现的（排错方法本身）

```bash
stat -c '%y' out/miplinux-*.iso installer/backend/mipl_installer/configure.py
```

ISO 的 mtime 比代码文件的 mtime 旧 → 这一圈的产物不含当前代码 → 先重建，再跑验收。
发现成本就是这一条 `stat`；没做这一步，代价是整轮 QEMU 的判据全部作废。

（安装器端到端验证）作为前置条件：ISO 必须比代码新，否则不跑这一圈。
