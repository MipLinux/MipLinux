# 05 · 测试方法

> 这篇文档说明如何验证 ISO 和安装结果，以及哪些东西必须在哪里测。

---

## 1. 核心原则

> **安装器（以及整个 ISO）直到「它装出来的系统能启动」之前，都不算被测过。**

---

## 2. 三个测试层次

| 层次 | 工具 | 能测什么 |
|---|---|---|
| 静态检查 | `mount` / `guestmount` | 文件是否存在、权限、配置内容 |
| 完整启动 | QEMU + KVM | 引导、安装、装后系统启动 |
| 终验 | 真机 | NVIDIA 驱动、双系统、畸形硬件 |

---

## 3. 准备测试环境

### 3.1 安装依赖

```bash
# Arch
sudo pacman -S edk2-ovmf qemu-desktop libguestfs

# 其他发行版的软件包请自行寻找
```

### 3.2 准备测试资产

```bash
# 空的目标虚拟盘
sudo ./scripts/mipl.sh target --force
```

> **`OVMF_VARS.fd` 必须每个测试用例单独复制一份。**
> UEFI 变量会被写入（引导项会留在 NVRAM 里），共用一份会导致后续测试结果不可信。这种污染很隐蔽——表现为「上次明明能引导，这次不行了」。
>
> **A5 起这条规则有两种执行方式，脚本已经替你分好：**
>
> | 用例 | 变量文件 | 行为 |
> |---|---|---|
> | 反复引导**同一个 ISO** | `out/OVMF_VARS.fd` | 每次 `mipl qemu` 都**刷新**（保持「干净变量」） |
> | **装好系统的盘** | `out/<盘名>.vars.fd`（如 `out/target.vars.fd`） | 跟着盘走、**保留** —— 装完重启进新系统靠的就是它 |
>
> 两份互不干扰：测 ISO 不会把装好系统的引导项刷掉。要单独清空某一份：`--fresh-vars`。

## 4. QEMU 启动命令

**用脚本，别手抄**（A5 起）：

```bash
sudo ./scripts/mipl.sh qemu                                # 只起 Live（不挂盘）
sudo ./scripts/mipl.sh installer                           # 装系统测试一条龙：建盘 + 挂盘 + 串口日志
sudo ./scripts/mipl.sh qemu --disk target.qcow2            # 装：ISO 优先 + 挂盘
sudo ./scripts/mipl.sh qemu --disk target.qcow2 --boot c   # 装完：不挂 ISO，从盘启动
```

**测安装器优先用 `installer`** —— 它比手工 `qemu --disk` 少记三件事：目标盘缺了自动建、
自动挂上、串口日志默认落 `out/installer-serial.log`。三条命令的差别与用法见
[tech/04](../work/tech/04-安装逻辑与实测.md) §2。

脚本替你处理的事，出问题时按这张表对照：

| 环节 | 脚本怎么处理 | 手抄会怎样 |
|---|---|---|
| UEFI 固件 | **运行时探测** OVMF 路径（Arch / Fedora / Debian 各不相同），两块 pflash 一个只读（`CODE`）一个可写（`VARS`） | 路径写死 → 换台机器就起不来 |
| 变量存储 | 每次 ISO 测试刷新 `OVMF_VARS`；装系统的目标盘另有自己的 NVRAM，**保留** | 把盘上的 NVRAM 一起刷掉 → 引导项丢失 |
| 磁盘 | `-drive file=…,if=virtio,format=qcow2`，参数用数组拼装 | 换行把参数拆开（Issue #8） |
| 引导顺序 | 测 Live 用光驱优先；`--boot c` 改成从盘启动 | 盘上没引导项时悄悄回到 Live，看着像「装成功了」 |
| 网络 | 用户模式网络，安装器能访问外网 | —— |
| 硬件加速 | `-enable-kvm` | —— |

**也不要绕过脚本去用 `run_archiso`** 这类辅助脚本 —— 它不挂目标盘、不处理 NVRAM，测不了装后系统，
等于给自己开了另一条没人维护的路径。

## 5. 六个必须验证的检查点

按顺序执行，任一步失败就停下排查。

| # | 检查内容 | 失败意味着 |
|---|---|---|
| 1 | ISO 启动，进入 Live 环境 | 引导配置错误，或包缺失 |
| 2 | 安装器界面自动出现（不要求登录，也不要求手动启动） | kiosk 链断在某一环（unit / 入口 / seat），一步步看 [tech/04](../work/tech/04-安装逻辑与实测.md) §3 |
| 3 | 安装器可操作：认得出磁盘、配得上网络 | 权限不足、依赖缺失，或网络栈配置错误 |
| 4 | **从目标盘重启，系统能启动** | ← **最关键，最常被跳过** |
| 5 | 装后系统内：用户、locale、输入法、字体正确 | 后置配置脚本未生效 |
| 6 | **装后系统能正常滚动升级**（`pacman -Syu`） | 仓库、密钥或镜像源配置错误 |

### 关于检查点 2 和 3

Live 环境是安装器的载体：开机后由 `mipl-installer.service` **直接**拉起 kiosk，
路径上没有别的环节。所以这两条是同一件事的两面 —— **安装器要能自己出现在屏幕上（2），并且真的能用（3）**。

> `getty` 的 autologin **不是进安装器的路径，是兜底**：unit 里有 `Conflicts=getty@tty1.service`，
> 安装器一起来就让位；安装器挂了或被 kill 掉，tty1 还能拿回来敲命令。
> 所以「能不能自动登录」验不出检查点 2，「不碰键盘窗口就出来」才作数。
> 启动链逐步拆解见 [tech/04](../work/tech/04-安装逻辑与实测.md) §1。

检查点 3 里的「配得上网络」是在线安装带来的硬要求：装系统时要能从仓库拉包。
QEMU 用用户模式网络（第 4 节的 `-netdev user`）时默认就能出网；真机上则要看 Live 能不能
连上 Wi-Fi —— Live 的联网后端是 NetworkManager（`nmcli`）。

### 关于检查点 6

这一条值得单独强调。自制发行版的典型长期故障是：

> 能装、能用，但用户第一次系统升级就崩溃。

常见原因：

- `pacman-key --init` 和 `--populate archlinux` 未在目标系统执行
- 目标系统的 `mirrorlist` 指向错误或不可用的地址
- 混入了构建机的配置

**必须在每次发版前手工验证这一条。**

## 6. 静态检查（不开机）

调配置时，先挂载检查比启动快一个数量级。

### 6.1 检查 ISO 内容

```bash
sudo mount -o loop,ro out/miplinux-*.iso /mnt
```

### 6.2 检查装完的虚拟盘

```bash
sudo guestmount -a out/target.qcow2 -i /mnt
```

可以直接确认：

- `/etc/passwd`、`/etc/group` —— 用户是否正确创建
- `/etc/locale.conf` —— 语言设置
- `/etc/pacman.d/mirrorlist` —— **镜像源是否已继承**
- `/usr/lib/modprobe.d/` —— NVIDIA 相关配置是否存在
- `/etc/fonts/local.conf` —— 字体 fallback

检查完记得 `sudo guestunmount /mnt`。

## 7. QEMU 与真机的分工

| 测试项 | QEMU | 真机 |
|---|---|---|
| 包是否正确安装 | ✅ | — |
| 引导流程 | ✅ | — |
| 安装器界面与流程 | ✅ | — |
| 分区逻辑 | ✅ | — |
| 装后系统启动 | ✅ | — |
| **NVIDIA 驱动加载** | ❌ | ✅ **唯一手段** |
| **双系统 / 已有 ESP** | ❌ | ✅ **唯一手段** |
| **EFI 固件差异** | ❌ | ✅ （某些主板行为不同） |
| **真实磁盘与 NVMe** | ❌ | ✅ |

## 8. 安全规则

> **分区代码的缺陷会摧毁数据。**
>
> **区逻辑的测试，优先在虚拟磁盘上测试，最后使用真实硬盘测试。**

具体建议：

1. 日常开发全部在 `target.qcow2` 上测试
2. 真机测试使用**独立的硬盘或旧机器**
3. **第一版不要实现「调整已有分区大小」** —— 无损 resize 要做到不出错，得靠 `kpmcore` 这类久经使用的分区库；自己实现极易造成数据丢失

## 9. 关于自动化

QEMU 支持 QMP 接口，可以通过脚本模拟按键、截图、抓取串口输出，实现自动回归测试。

## 10. 构建产物的一致性验证

由于维护者的宿主机发行版不同，需要确保各自构建的结果一致。

**验证方法：**

将构建放进 systemd-nspawn 的纯 Arch 容器中，且 profile 的 `pacman.conf` 不使用 `Include`（详见 [02-环境与工具链.md](02-环境与工具链.md) 第 3.1 节与 [03-项目结构.md](03-项目结构.md) 第 4 节）。

**验证步骤：**

1. 各自在同一 commit 上构建一次
2. 对比产物的 SHA256

> 注意：由于包版本是滚动的，**不同日期构建的产物不可能一致**，这是正常的。
> 一致性验证应在**同一天**、使用**同一份镜像快照**的前提下进行。

## 11. 安装器的端到端验证

安装器**在它装出来的系统能启动之前都不算被测过**（第 1 节）。用现成的命令就能跑完整条链。

**前置（每圈第 0 步）：先对时间戳。** 验收跑的是 ISO 里**打包进去**的代码，不是工作树 ——
ISO 必须比代码新，否则这一圈验的是修复前的代码（09-25 就白跑过一整圈：17:02 的 ISO
装的是 17:59 修复前的代码，完整记录见 [archive](../archive/2026-09-25-ISO装的是修复前的代码.md)）。

```bash
stat -c '%y' out/miplinux-*.iso installer/backend/mipl_installer/configure.py  # 0. 对时间戳：ISO 必须比代码新
sudo ./scripts/mipl.sh installer                            # 1+2. 建盘（缺了才建）→ 进 Live 跑安装

# Live 里（root shell）驱动安装器（完整参数见 `python3 -m mipl_installer --help`）：
lsblk -o NAME,SIZE,TYPE,MOUNTPOINTS                     # 先认目标盘，通常是 /dev/vda
printf '%s\n' '密码' | PYTHONPATH=/usr/local/lib/mipl-installer/backend \
     python3 -m mipl_installer --disk /dev/vda --yes --password-stdin
   poweroff                                                # 装完关机

sudo ./scripts/mipl.sh installer --boot c                   # 3. 检查点 4：从盘启动
```

（等价的显式写法是 `target --force` + `qemu --disk …` + `qemu --disk … --boot c` 三段，
见 [installer/AGENTS.md](../../installer/AGENTS.md)；`installer` 只是把前两段合成一条。
密码只走 stdin、不进 argv —— 密码占了 stdin，`confirm()` 走到 `sys.stdin.isatty()` 判非交互，
没有 `--yes` 就直接硬失败（`[失败] 非交互环境要显式 --yes`），所以 `--yes` **不是可选项**：
它跳过的是整盘擦除的确认，不是密码。
不设 root 密码则 root 保持锁定、只用 sudo 提权 —— 要设就加
`--root-password-stdin`，stdin 再给一行 root 密码，用户在前、root 在后。）

逐条确认什么，以及检查点 2 / 3 在 M0 阶段验到哪一步，见
[tech/04-安装逻辑与实测](../work/tech/04-安装逻辑与实测.md) §3 与 §5。

然后逐条确认：

| 验什么 | 怎么验 |
|---|---|
| 引导项写对了 | `--boot c` 能进系统；盘上没引导项时脚本会明确报 `no bootable device`，不会悄悄回到 Live |
| 分区与文件系统 | `guestmount -a out/target.qcow2 -i /mnt`，看 `/etc/fstab` 里的 UUID 与 `lsblk` 是否对得上（第 6.2 节） |
| 继承了国内源 | `/etc/pacman.d/mirrorlist` 指向国内镜像，而不是官方源 |
| NVIDIA DRM 模式设置 | 装后系统执行 `cat /sys/module/nvidia_drm/parameters/modeset`，输出 `Y` |
| 能滚动升级 | 装后系统里 `pacman -Syu`（检查点 6） |

**全过程只在 `out/target.qcow2` 上做**（第 8 节）。真机只用于 QEMU 测不了的部分：
NVIDIA 驱动、已有分区与双系统、EFI 固件差异。
