# 技术细节 01 · 容器环境搭建

> 目标：建立一个纯净的 Arch 构建环境，且宿主机无论是 CachyOS 还是 Fedora 都能用。
>
> 产物：一个可以反复进入的容器 `/var/lib/machines/archbuild`。

---

## 前置条件

宿主机需要：

| 项 | 要求 | 检查命令 |
|---|---|---|
| `systemd-nspawn` | 随 systemd 提供 | `command -v systemd-nspawn` |
| 磁盘空间 | ≥ 20 GB 空闲 | `df -h /var/lib/machines` |
| 网络 | 能访问镜像站 | — |

**不需要**在宿主机安装 `archiso`、`pacstrap`、`mkarchiso`——这些都在容器里。

### 本机现状（已确认）

| 项 | 状态 |
|---|---|
| `systemd-nspawn` | ✅ `/usr/bin/systemd-nspawn`（systemd 261） |
| `machinectl` | ✅ |
| 磁盘可用 | ✅ 608 GB |
| `archiso` | ❌ 未安装 —— **正常，在容器里装** |

## 步骤 1 · 下载 Arch bootstrap

```bash
cd /tmp
curl -LO https://mirrors.tuna.tsinghua.edu.cn/archlinux/iso/latest/archlinux-bootstrap-x86_64.tar.zst
```

**校验（必须做，不是建议）：**

```bash
curl -LO https://mirrors.tuna.tsinghua.edu.cn/archlinux/iso/latest/sha256sums.txt
sha256sum -c --ignore-missing sha256sums.txt
```

> `--ignore-missing` 是必需的，因为 `sha256sums.txt` 包含 ISO 等其它文件的校验和。

> **为什么是「必须」**：`sha256sums.txt` 里的版本号会变（例如现在是
> `archlinux-bootstrap-2026.09.01-x86_64.tar.zst`）。如果被截断的旧文件还躺在
> `/tmp`，`curl -LO` 会**直接跳过下载**（文件已存在），你会拿着半截文件一路走到
> 解压才炸，而炸出来的现场极难判断 —— 见「常见问题」里的
> **nspawn 报 execv failed**。
> 想彻底避免这件事，用仓库的脚本（它下载前后都会校验）：
> `sudo ./scripts/mipl.sh build`。

**预期：** 约 120 MB 的 `.tar.zst` 文件。

**备用镜像**（TUNA 不通时）：

- 官方：`https://geo.mirror.pkgbuild.com/iso/latest/`
- 中科大：`https://mirrors.ustc.edu.cn/archlinux/iso/latest/`
- 阿里云：`https://mirrors.aliyun.com/archlinux/iso/latest/`

## 步骤 2 · 解压成容器

```bash
sudo mkdir -p /var/lib/machines/archbuild

sudo tar --numeric-owner -xpf archlinux-bootstrap-x86_64.tar.zst \
     -C /var/lib/machines/archbuild --strip-components=1
```

**两个参数都不能少：**

| 参数 | 作用 | 少了会怎样 |
|---|---|---|
| `--numeric-owner` | 按数字保留 uid/gid | 权限混乱，容器内 root 身份异常 |
| `--strip-components=1` | 去掉顶层的 `root.x86_64/` 目录 | 文件被埋在 `archbuild/root.x86_64/` 下，nspawn 找不到 |

**验证解压结果：**

```bash
ls /var/lib/machines/archbuild/
# 应该直接看到 bin/ etc/ usr/ var/ 等，而不是 root.x86_64/
```

**但只看到 `etc/` 不算数 —— 要验「能不能用」：**

```bash
ls /var/lib/machines/archbuild/usr/bin/bash      # 能执行的 shell
ls /var/lib/machines/archbuild/usr/lib/ld-linux-x86-64.so.2
```

`etc/os-release` 在这份归档里排**第 630 条**，而 `usr/bin/bash` 排**第 5815 条**
（共 33105 条）。所以一次被中断的解压，恰好会留下 `etc/os-release` 却不留
`bash` —— 目录看起来正常，直到 `systemd-nspawn` 抛出一句
`execv(/bin/bash, /bin/bash, /bin/sh) failed: No such file or directory`。
判断容器好没好，请看上面的两个文件，或者直接用：

```bash
sudo ./scripts/mipl.sh doctor      # 会报 [ok] container ...（已初始化，shell /usr/bin/sh）
```

## 步骤 3 · 准备输出目录并进入容器

**这一步要决定：ISO 产物放在哪里。**

推荐直接绑定到项目目录，这样构建完 QEMU 能立刻用：

```bash
mkdir -p ~/Code/Projects/MipLinux/out

sudo systemd-nspawn -D /var/lib/machines/archbuild \
     -u root \
     --bind ~/Code/Projects/MipLinux/out:/out
```

**参数说明：**

| 参数 | 作用 |
|---|---|
| `-D <dir>` | 用哪个目录作为容器根 |
| `-u root` | 以 root 身份运行（见下方说明） |
| `--bind <宿主>:<容器>` | 把宿主目录挂进容器 |

**注意：** `--bind` 的目标路径 `/out` 在容器内必须不存在或为空。如果你想用别的挂载点，改成对应路径。

**预期：** 直接得到一个 root shell，类似：

```
[root@archbuild /]#
```

### ⚠️ 不要加 `-b`

**这是本文档最容易出错的一处。**

`systemd-nspawn` 手册对 `-b` 的说明：

> `-b, --boot` — Automatically search for an init program and invoke it as PID 1, instead of a shell or a user supplied program.

加了 `-b` 会得到两件事，都是你不想要的：

| 后果 | 说明 |
|---|---|
| **需要登录** | 容器跑完整 systemd，停在 `archbuild login:` 提示符 |
| **无法登录** | bootstrap 的 `/etc/shadow` 中 root 是 `root:*:...` —— `*` 表示没有有效密码，任何输入都不被接受 |

**实测确认的 root 账户状态：**

```
$ tar xf archlinux-bootstrap-x86_64.tar.zst -C /tmp root.x86_64/etc/shadow
$ grep '^root:' /tmp/root.x86_64/etc/shadow
root:*:14871::::::
```

`*` 不是密码哈希，而是「禁止密码登录」的标记。**这不是你操作错了，是 bootstrap 的设计如此**——它本来就不打算让你登录进去。

**另一个隐蔽问题：** 一旦用了 `-b`，命令行上的任何附加参数都会被当作 **init 的参数**传给 systemd，而不是当作要执行的命令。所以下面这种写法是无效的：

```bash
# ✗ 错误：-b 会把 "/root/build.sh" 当成给 systemd 的参数，不会执行它
systemd-nspawn -D <dir> -b /root/build.sh
```

### 为什么不需要 `-b`

构建 ISO **不需要容器里有 init 在跑**。容器只需要是一个能执行命令的 root 环境：

- `mkarchiso` 是普通脚本，直接执行即可
- `pacstrap` / `mkinitcpio` 也都通过 `chroot` 到目标目录工作，不依赖宿主容器的 systemd
- 需要网络，而 nspawn 默认共享宿主机网络命名空间，无需 systemd-networkd

**结论：不引导，只当环境用。** 这也更快——省掉整套 systemd 启动。

> 本节曾给出的命令带有 `-b`，导致无法登录。已在 2026-09-17 修正。

### 如果确实需要引导容器

只有在需要容器内的 systemd 服务（如 `systemd-networkd`、`systemd-resolved`）时才有必要。此时需要先设置密码：

```bash
# 不引导进入容器
sudo systemd-nspawn -D /var/lib/machines/archbuild -u root

# 在里面设置密码
passwd

# 退出后带 -b 进入，即可用该密码登录
sudo systemd-nspawn -D /var/lib/machines/archbuild -b
```

**本项目的构建流程不需要这样做。**

## 步骤 4 · 容器内初始化（仅首次）

### 4.1 初始化 pacman 密钥环

```bash
pacman-key --init
pacman-key --populate archlinux
```

> **这一步不能跳过。**
>
> bootstrap tarball 的密钥环是空的。不初始化的话，所有包签名校验都会失败，`pacman -S` 会报 `invalid or corrupted package (PGP signature)`。

### 4.2 更新系统并安装构建工具链

```bash
pacman -Syu
pacman -S archiso
```

**`archiso` 会自动带入全部构建依赖：**

```
arch-install-scripts    提供 pacstrap / arch-chroot
bash
dosfstools              提供 mkfs.vfat
e2fsprogs               提供 mkfs.ext4
erofs-utils             提供 mkfs.erofs
libarchive
libisoburn              提供 xorriso
mtools
squashfs-tools          提供 mksquashfs
```

**不需要**在容器里装 `qemu-desktop` 或 `edk2-ovmf`——测试在宿主机上做。

### 4.3 验证工具链完整

```bash
for c in mkarchiso pacstrap arch-chroot mkinitcpio mksquashfs xorriso mkfs.vfat; do
  printf "%-14s " "$c"
  command -v $c >/dev/null 2>&1 && echo "✓" || echo "✗ 缺失"
done
```

**全部应为 ✓。**

## 步骤 5 · 退出与再次进入

> **这一节很重要。** 容器不会因为你关闭终端而停止，错误的退出方式会留下残留状态，导致下次无法进入。详见[容器生命周期](#容器生命周期必须理解的一节)。

### 退出（推荐方式）

```bash
# 在容器内
poweroff
```

或者退出 shell 后，在宿主机干净关掉：

```bash
sudo machinectl poweroff archbuild
```

### 再次进入（后续日常使用）

```bash
sudo systemd-nspawn -D /var/lib/machines/archbuild \
     -u root \
     --bind ~/Code/Projects/MipLinux/out:/out
```

**不需要重复步骤 4**——容器状态是持久的。

## 容器生命周期（必须理解的一节）

### 终端 ≠ 容器

这是最容易误解的一点：

| | 是什么 | 关闭它会怎样 |
|---|---|---|
| **终端 / 会话** | 接到容器控制台的一个连接 | 只是断开连接，**容器继续运行** |
| **容器** | systemd 管理的一个 machine（`archbuild.scope`） | 需要显式 `poweroff` / `terminate` 才会停止 |

**容器是「启动了就一直在」的东西。** 直接关掉终端窗口，容器不会消失——它会继续运行并**继续占用 `archbuild` 这个机器名**。

### 机器名的占用规则

`systemd-nspawn` **用 `-D` 目录的 basename 作为机器名**（`-D .../archbuild` → 机器名 `archbuild`）。这个名字用于：

- `/run/systemd/nspawn/<机器名>/` 下的运行时目录
- `/run/systemd/machines/<机器名>` 的注册
- `archbuild.scope` 这个 unit

**同一时刻只能有一个叫 `archbuild` 的容器。** 上一个没退出，下一个就进不来，报：

```
Mount point '/run/systemd/nspawn/archbuild/unix-export' exists already, refusing.
```

**这个报错信息具有误导性**——它说的是挂载点冲突，真实原因是机器名被占用。看到它时，第一反应应该是「是不是还有个容器在跑」，而不是去查挂载点。

### 检查容器的实际状态

```bash
machinectl list                    # 有没有在跑的容器
machinectl status archbuild        # 详情：启动时间、Leader PID、内部服务
```

`machinectl status` 会显示 `Since:`（启动时间）和 `Leader:`（容器内 systemd 的 PID）。**如果这两项存在且进程还活着，容器就在运行。**

### 终端已经关掉了怎么办

**不要紧，容器不依赖那个终端。** 两条路：

#### 方案 1 · 收掉重开（最简单）

```bash
sudo machinectl poweroff archbuild     # 干净关机（容器里是 systemd，这个能用）
# 或
sudo machinectl terminate archbuild    # 强杀，不留清理时间

machinectl list                        # 确认列表为空
```

两个命令的区别（`man machinectl`）：

| 命令 | 行为 |
|---|---|
| `poweroff` | 向容器 init 发 `SIGRTMIN+4`，**走正常关机流程** |
| `terminate` | **立即杀死**所有进程并释放资源，不做清理 |

然后按正常方式重新进入即可。**代价是容器内未保存的状态会丢失**——如果里面没有正在跑的长任务，直接 `terminate` 最省事。

#### 方案 2 · 钻进正在跑的容器（不重启）

`machinectl login` 会**新开一个终端**接到容器的控制台，不需要重启容器：

```bash
sudo machinectl login archbuild
```

进去后可以顺手修掉那个「无法登录」的根因：

```bash
passwd            # 给 root 设密码 ← 设完以后用 -b 也能正常登录
exit
```

> 若 `machinectl login` 不可用，还可用底层手段 `nsenter`：
> ```bash
> machinectl status archbuild | grep Leader      # 取 Leader PID
> sudo nsenter -t <PID> -a
> ```
> `machinectl` 内部做的也是同一件事。

### ⚠️ 不要用 `Ctrl+]` 三次

在宿主机按 `Ctrl+]` 三次会强杀容器，**可能留下残留状态**（运行时目录、machine 注册、scope unit 没被清理），下次进入就会遇到机器名冲突。

**这是产生本文档所述故障的典型路径。** 请用 `poweroff`。

### 需要并行开多个会话时

用 `--machine=` 给每次调用不同的名字，避免撞名：

```bash
sudo systemd-nspawn -D /var/lib/machines/archbuild \
     --machine=archbuild-build1 \
     -u root \
     --bind ~/Code/Projects/MipLinux/out:/out
```

否则两次调用都想叫 `archbuild`，第二个必然失败。正常流程下一次只用一个会话，干净退出就够了。

### 一句话规则

> **每次用完，在容器内 `poweroff`，或在宿主机 `machinectl poweroff <名字>`。**
> **不要关窗口，不要按 `Ctrl+]`。**

## 常见问题

### 报 `Mount point '.../unix-export' exists already, refusing.`

**真实原因不是挂载点，而是机器名 `archbuild` 已被占用**——多半是上一次的容器还在运行（常见于直接关掉了终端窗口）。

```bash
machinectl list                    # 看有没有在跑的容器
machinectl status archbuild        # 看 Since / Leader

sudo machinectl poweroff archbuild # 收掉旧的
machinectl list                    # 确认为空
```

然后重新进入即可。详见[容器生命周期](#容器生命周期必须理解的一节)。

### 停在 `archbuild login:`，输入任何密码都进不去

**原因：命令里带了 `-b`。**

bootstrap 的 `/etc/shadow` 中 root 是 `root:*:...`，`*` 表示没有有效密码，所以登录必然失败。

**解决：去掉 `-b`，改为 `-u root`。**

```bash
sudo systemd-nspawn -D /var/lib/machines/archbuild -u root
```

详见步骤 3 的说明。**这是本流程最常见的错误，且报错信息具有误导性**——看起来像是密码错了，实际上是没有密码。

> 如果你已经处于这个状态（容器带 `-b` 跑着但登不进去），见[容器生命周期](#容器生命周期必须理解的一节)的「终端已经关掉了怎么办」。

### `-b` 后面跟的脚本没有执行

`-b` 会把命令行参数当作 **init 的参数**，而不是要执行的命令。去掉 `-b` 即可。

### `pacman -S` 报 PGP 签名错误

密钥环没初始化。回到步骤 4.1。

### nspawn 启动报找不到 init 或 os-release

解压时漏了 `--strip-components=1`，文件被埋在 `root.x86_64/` 下。重新解压。

### nspawn 报 execv failed，说 No such file or directory

**这不是权限问题，也不是 nspawn 的毛病 —— 容器里没有能执行的 shell。**

`systemd-nspawn` 不带命令时会按 `/bin/bash` → `/bin/sh` 的顺序找一个能用的
shell；这句报错的意思是这两个（在容器里是同一个 symlink）都执行不了。

**成因**：解压被中断（Ctrl-C、断线、盘满、归档本身是半截的）。
`etc/os-release` 在归档里排第 630 条、`usr/bin/bash` 排第 5815 条，
所以半成品恰好会留下 `os-release`，于是所有「文件在不在」的检查都说 OK。

**先确认：**

```bash
ls /var/lib/machines/archbuild/usr/bin/bash
zstd -t /tmp/archlinux-bootstrap-x86_64.tar.zst     # 半截文件在这里就会报
#   报 `premature end` 就是它 —— 归档本身不完整
```

**重建**（残缺的目录必须删掉，否则下次运行还会把它当成「已初始化」）：

```bash
sudo rm -rf /var/lib/machines/archbuild
sudo rm -f /tmp/archlinux-bootstrap-x86_64.tar.zst*   # 连半截缓存一起清
sudo ./scripts/mipl.sh build
```

**脚本现在已经会自己认出这些情况**（Issue #32）：缓存先过 `sha256` 与 `zstd`
完整性，坏了就删掉重下；解压前后各查一次容器是否真的能用；`mipl doctor` 会直接报
`[!!] container ...（残缺！缺：...）`，而不是一句「已初始化」。要手清缓存：
`sudo ./scripts/mipl.sh clean --bootstrap`。

### 解压时大量 `无法创建符号连接：权限不够`

`tar` 命令没有用 `sudo`。bootstrap 中包含需要 root 权限的符号链接与 capabilities。

**注意：这类错误不会让 `tar` 返回非零退出码**，容易误以为解压成功。解压后务必检查：

```bash
sudo ls /var/lib/machines/archbuild/etc/ca-certificates/extracted/cadir/ | head
```

应当看到大量 `.0` 链接文件。

### 容器内网络不通

检查宿主机网络。nspawn 默认使用宿主机的网络命名空间，通常无需额外配置。

### `--bind` 报目标路径已存在

容器内的挂载点必须不存在或为空目录。换个路径，或先在容器内清空。
