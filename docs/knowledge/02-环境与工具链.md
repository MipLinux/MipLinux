# 02 · 环境与工具链

> 这篇文档说明每样工具是什么、为什么需要它，以及**怎么在你自己机器上确认它可用**。

---

## 1. 工具清单

### 1.1 `archiso`

一个 Arch 软件包，提供两样东西：

| 内容 | 路径 | 作用 |
|---|---|---|
| `mkarchiso` | `/usr/bin/mkarchiso` | 真正的构建程序，一个 bash 脚本 |
| `run_archiso` | `/usr/bin/run_archiso` | 构建完直接 QEMU 启动的辅助脚本 |
| 参考 profile | `/usr/share/archiso/configs/` | `releng`（完整 Live）与 `baseline`（最小） |

**三个容易混淆的名字：**

- **`archiso`** —— 软件包
- **`mkarchiso`** —— 包里的构建脚本
- **profile** —— 你的配置目录，`releng` 是官方参考实现

### 1.2 `mkarchiso` 的完整流水线

按源码顺序：

```
1. 读 profiledef.sh                 ← 发行版身份、引导方式、压缩算法
2. 读 profile/pacman.conf
   └─ 在【宿主机】上解析 Include     ← ★ 陷阱所在，见第 3 节
3. pacstrap 一个空目录
   └─ 按 packages.x86_64 下载安装所有包
4. cp -af profile/airootfs/. → 该目录
5. 按 file_permissions 数组重设权限
6. 在该目录内运行 mkinitcpio        ← 生成 Live 环境自己的 initramfs
7. 清理（缓存、日志、machine-id）
8. mksquashfs → airootfs.sfs         ← 整个系统变成一个只读压缩包
9. xorriso → .iso                    ← 加引导器、EFI 分区，产出成品
```

**第 3 步就是「装一个完整的 Arch 系统」**，这是理解 mkarchiso 的关键。

### 1.3 `systemd-nspawn`

systemd 自带的轻量容器工具，**属于 `systemd` 包，无需额外安装**。

#### 隔离手段谱系

| 手段 | 隔离程度 | 里面是什么 | 能否装另一个发行版 |
|---|---|---|---|
| `chroot` | 极弱 | 只是换个根目录 | 能，但很脏 |
| **`systemd-nspawn`** | 中 | 一个跑着 systemd 的完整用户空间 | **能，很干净** |
| Docker / Podman | 中 | 同上，额外管镜像分层 | 能 |
| 虚拟机 | 强 | 整个内核 + 用户空间 | 能，但重 |

#### 为什么 chroot 不够

`chroot` 只换了文件的根目录，进程与宿主机共享同一内核、同一 PID 空间、同一 `/proc`。在里面跑 `pacman` 会看到宿主机的进程表，很多操作会莫名失败或污染宿主机。

`systemd-nspawn` 提供：

- 独立的 PID / 挂载 / 网络 / UTS 命名空间
- 容器内运行自己的 systemd 作为 1 号进程
- 独立的 `/proc`、`/sys`、`/dev`

它**就是 systemd 项目自己的 chroot 替代品**，也是 Arch Wiki 推荐的从零安装方式之一。

#### 建立构建环境

我们一律使用脚本：

```bash
sudo ./scripts/mipl.sh build    # 第一次会顺带把构建环境建起来，然后开始构建
sudo ./scripts/mipl.sh shell    # 之后想进容器看看，用这条（容器还不存在时它会让你先跑 build）
sudo ./scripts/mipl.sh stop     # 关掉容器，当然你也可以直接关闭 QEMU 窗口结束
```

> **容器生命周期：** 容器由 systemd 作为 `archbuild.scope` 管理，关掉终端**不会**让它停止。
> 
> 机器名被占用的报错与处理见 [tech/01](../work/tech/01-容器环境搭建.md)。

#### nspawn 与 Docker 的取舍

| | systemd-nspawn | Docker |
|---|---|---|
| 安装 | systemd 自带 | 需单独安装 |
| 操作对象 | 直接是一个目录，可直观查看改动 | 镜像分层，需 `commit` 才持久 |
| 生态 | 无 | CI 集成成熟 |

**推荐 nspawn**：因为它直接操作目录，调试构建环境时更直观，也更容易被构建脚本自动化重建。

### 1.4 QEMU / KVM

测试环境。**必须在宿主机上运行，不能在 nspawn 里运行**（原因见 [01-概念模型.md](01-概念模型.md) 第 4 节）。

```bash
sudo ./scripts/mipl.sh target --force
sudo ./scripts/mipl.sh qemu
sudo ./scripts/mipl.sh installer --serial console
```

### 1.5 其它工具

| 工具 | 来源 | 用途 |
|---|---|---|
| `pacstrap` | `arch-install-scripts` | 把包解开到目标目录 |
| `arch-chroot` | `arch-install-scripts` | 进入目标系统执行配置 |
| `mkinitcpio` | `mkinitcpio` | 生成 initramfs |
| `mksquashfs` | `squashfs-tools` | 压缩根文件系统 |
| `xorriso` | `libisoburn` | 组装 ISO |
| `shellcheck` | `shellcheck` | archiso 自带的代码检查目标 |

## 2. 怎么看你自己的机器

**每台机器装了什么、能不能用，只有本机跑一遍才知道** —— 所以这一节不列「本机已具备什么」，只讲怎么看、
以及看到什么算合格。换机器、换人接手，第一件事都是：

```bash
sudo ./scripts/mipl.sh doctor      # 逐项探测并给出结论；--report 输出可粘进 issue 的表格
```

### 2.1 宿主机需要什么，不需要什么

| | 需要 | 不需要 |
|---|---|---|
| 宿主机 | `systemd-nspawn`（构建容器）、QEMU + OVMF（引导测试）、`/dev/kvm` | `mkarchiso` / `pacstrap` / `xorriso` / `mksquashfs` —— 这些在容器里 |
| 容器 | `pacman` 能联网、`archiso`、`mkinitcpio`、`arch-install-scripts` | 宿主机的包管理器与源配置 |

**宿主机没装构建工具是正常的，不是缺陷。** 构建一律在 nspawn 容器里做，为的是不把宿主发行版的软件源
静默带进产物（见第 3 节）。所以 `doctor` 报「宿主缺 `mkarchiso`」不代表环境不可用 —— 它只报事实，
合格与否按 `doctor` 的结论行看。

### 2.2 这个项目要用的包，都在官方仓库里

下表是**包与仓库的对应关系**，不是版本清单：它要证明的是「本项目不需要任何第三方源」。
版本随时间滚动，要当前值就查仓库或用 `pacman -Si`。

**构建链（都装在容器里）：**

| 包名 | 仓库 | 用途 |
|---|---|---|
| `archiso` | extra | 构建工具，提供 `mkarchiso` |
| `mkinitcpio` | core | 生成 initramfs —— **`archiso` 不会自动带上它** |
| `squashfs-tools` | core | `mksquashfs`，把系统压成一个只读镜像 |
| `libisoburn` | extra | `xorriso`，把镜像组装成 ISO |
| `arch-install-scripts` | core | `pacstrap` / `arch-chroot`：装系统的两个核心动作 |
| `archinstall` | extra | 官方安装器；本项目只借它验证「装完能启动」这条链路 |

**内核：**

| 包名 | 仓库 | 用途 |
|---|---|---|
| `linux` | core | 唯一支持的内核 —— 原因见 [04-架构决策.md](04-架构决策.md) 第 1.3 节 |

**NVIDIA 相关：**

| 包名 | 仓库 | 说明 |
|---|---|---|
| `nvidia-open` | extra | 开核模块，**硬绑官方 `linux` 内核、并锁死配套的 `nvidia-utils` 版本** —— 换非官方内核就装不上 |
| `nvidia-open-dkms` | extra | 开核模块源码，不绑定内核（本项目不用，见 [04-架构决策.md](04-架构决策.md) 的排除表） |
| `nvidia-open-lts` | extra | 对应 LTS 内核 |
| `nvidia-utils` | extra | 用户态工具，配 `nvidia-open` 使用 |
| `nvidia` / `nvidia-dkms` | — | **已不存在** —— NVIDIA 590 起主线包切到开核模块 |

要当前版本与依赖关系，查仓库或用 `pacman -Si nvidia-open`；本文不记快照。

**中文支持：**

| 包名 | 用途 |
|---|---|
| `noto-fonts-cjk` | 主力 CJK 字体 |
| `noto-fonts-emoji` | emoji —— 容易被忽略，但用户一开机就会看到 |
| `fcitx5` + `fcitx5-chinese-addons` | 输入法框架与拼音方案 |
| `fcitx5-configtool` | 输入法配置界面 |
| `fcitx5-gtk` / `fcitx5-qt` | GTK / Qt 程序里的输入法支持 |

这些同样都在官方仓库；版本以构建当天的仓库为准。

**Live 环境的联网：**

| 包名 | 用途 |
|---|---|
| `networkmanager` | Live 的联网后端：有线插上即用，无线用 `nmcli` 选网（安装器直接调它） |

**安装器：**

| 包名 | 用途 |
|---|---|
| `python` | 安装器的核心逻辑 —— Live 里本来就有（`reflector` 依赖它） |
| `python-pyparted` | 分区：擦盘、建 GPT、ESP + root |
| `electron44` | 界面运行时（Chromium + Node）。官方 `extra`；钉版本化包名，不用 `electron` 元包 |
| `cage` | kiosk 合成器：全屏跑一个窗口，那个窗口就是安装器 |

**桌面：**

交付形态是 **WM 路线**（Wayland 平铺合成器），不做完整桌面环境 ——
所以本节没有 `plasma-desktop` 这类完整桌面包。
