## P1 · 发行版名称 — ✅ 已确定

**决定（D9）：名称是 MipLinux。标识取值如下：**

| 变量 | 取值 | 说明 |
|---|---|---|
| `iso_name` | `miplinux` | 产物名即 `miplinux-<日期>-x86_64.iso` |
| `iso_label` | `MIPLINUX_<YYYYMM>` | ISO9660 卷标。**不参与引导参数** —— 引导项用的是 `archisosearchuuid`（构建时生成的时间戳 UUID），所以换卷标不需要同步改引导配置 |
| `iso_publisher` | `MipLinux <https://github.com/MipLinux/>` | 带组织 URL —— P2 已定为对外发布，这条不用返工 |
| `iso_application` | `MipLinux Live/Install Medium` | 措辞中性；P4 已定为极简 kiosk，措辞仍然成立 |

**落地方式（A6）：** 9 个文件、26 处静态文本 —— `profile/profiledef.sh` 的四个变量，
加上 `efiboot/`、`syslinux/`、`grub/` 里的菜单标题与帮助文本。上游 `mkarchiso` 只替换
`%ARCH%` / `%INSTALL_DIR%` / `%ARCHISO_UUID%`，**没有名字占位符**，所以只能写死；
「有没有漏改」交给 `scripts/check-identity.sh` 断言（豁免项逐条带理由，
非 root 可跑，改名前后各跑一次即可看到红 → 绿）。

**已经落地但不在这份文档范围里的两处：** 卷标会同时写进 ISO 里的 `grubenv`
（`ARCHISO_LABEL=`），但那份文件由 `mkarchiso` 生成，改 `iso_label` 就自动跟着变。

**还没做的品牌露出（有意留白）：**

| 位置 | 现状 | 归属 |
|---|---|---|
| `airootfs/etc/motd` | 开机第一眼仍是 "Arch Linux" | 线 C 的文件 |
| `airootfs/etc/hostname` | 提示符仍是 `[root@archiso ~]#` —— 正好是「A6 没越界动别人文件」的证据 | 线 C 的文件 |
| `/etc/os-release` | Live 与装后系统里仍是 Arch 的（`filesystem` 包提供） | 品牌化阶段单独一轮 |
| 引导菜单以外的一切视觉（logo / 壁纸 / 主题） | 未开始 | 按计划排在功能之后，且受 P5 阻塞 |

## P2 · 目标范围 — ✅ 已确定

**决定（D10）：对外发布。** 交付对象不只是维护者自己，而是任何下载这份 ISO 的中文用户。

**这条为什么必须最先定：** 它决定后面所有工作的严格程度 —— 签名、文档、硬件覆盖都不是「以后补」，
而是发布流程的一部分。原来那张「自用 / 对外发布」的对比表，现在逐行落到具体要求上：

| 维度 | 自用时 | 对外发布后的要求 | 现状 |
|---|---|---|---|
| 签名 | 不需要 | ISO 要有 GPG 签名与 SHA256 校验和，Release 页给出验证步骤 | ❌ 未开始 |
| 软件仓库 | 不需要 | **只要不引入自建包，就不需要自建仓库。** P6 定为「后端自研」后，原本「为了分发 AUR 里的 Calamares 而建仓库」这个前提消失了 —— 但一旦将来引入自建包，这条会回来 | — 暂无需求 |
| 升级路径 | 无要求 | 用户能从旧版本升到新版本。Arch 滚动更新天然满足，前提是装后系统的 `mirrorlist` 与 keyring 正确（[05-测试方法.md](05-测试方法.md) 检查点 6） | 由 D7 覆盖 |
| 文档 | 随意 | 需要完整的中文安装与使用文档，随 Release 一起给出 | ❌ 未开始（[04-架构决策.md](04-架构决策.md) 第 2.5 节） |
| 硬件兼容 | 只需覆盖维护者自己的机器 | 要覆盖各种显卡、磁盘、主板；真机验证范围主动扩大，双系统与畸形分区必须测（[05-测试方法.md](05-测试方法.md) 第 7 节） | ❌ 未开始 |
| 缺陷容忍度 | 高 | 低：发布前六个检查点全跑一遍，且「用户手里是第几版」必须可辨识（→ D13） | — |

**必须写进发布说明的一条（P8 的保留事项现在生效）：**
本发行版不支持 Pascal 及更老的 NVIDIA 显卡（GTX 10 系及以前），这些卡只能用 `nouveau`。
详见 [04-架构决策.md](04-架构决策.md) 第 1.7 节。

## P3 · ISO 形态 — ✅ 已确定

**决定（D11）：在线安装。ISO 只承载 Live 环境；装系统所需的包在安装时从（国内）镜像仓库拉取。**

**理由：**

- ISO 小，构建、下载、写 U 盘都快
- 不用处理离线方案特有的那堆问题：包缓存目录、`pacman.conf` 的 `CacheDir`、体积与压缩策略的权衡
- 本项目的镜像源目标（[04-架构决策.md](04-架构决策.md) 第 2.4 节）本来就要把国内源做成默认 ——
  在线安装把这件事从「加分项」变成**前提**，等于吃自己配置的红利

**代价与随之而来的硬性要求：**

| 要求 | 说明 |
|---|---|
| **安装时必须联网** | 有线应当插上即用；**Wi-Fi 必须在安装器里能选 SSID、能输密码** —— 做不到这一点，用户在第一步就卡死。这是极简 Live 也**不能省**的功能（见 P4） |
| Wi-Fi 走哪套栈 | **NetworkManager + `nmcli`**（见 P6 / D14）：安装器直接调 `nmcli`。Live 里原来的 `iwd` 会被换掉（Issue #30：`iwctl` 不好用） |
| **国内源必须在「装之前」生效** | Live 的 `mirrorlist` 与写进目标系统的 `mirrorlist` 是同一份国内源。否则在线安装会走官方源，慢到不可用 |
| **N 卡驱动进 Live 清单** | `profile/packages.x86_64` 是 Live 的清单，已写进 `nvidia-open` + `nvidia-utils` —— 真机验证要先在 Live 里拿到「驱动能加载」的证据。代价是 ISO 体积（`nvidia-utils` 装完约 1 GB，见 [tech/02](../work/tech/02-构建与QEMU测试.md)）。装后系统装什么由装后基础清单 + 用户在安装器里勾选的应用决定（见 P10）。**验证点仍是两次**：Live 一次、装完重启一次 |
| 断网就装不了 | 有意接受 ——「插上 U 盘就能装完」被换成「插上 U 盘、连着网就能装完」。这一点要写进用户文档 |

**体积口径的变化：** 现有实测参照：ISO **1.5 GiB**（1,616,740,352 B）、构建约 **2 分 08 秒**；
基线 releng 与改名后的 MipLinux 产物同尺寸（差 0.002%，来自 initramfs 时间戳）。在线安装 + 极简 Live
之后，目标体积应当明显小于这个数，但**裁剪尚未开始**（见 P4 的裁剪清单）。

**被否决的方案：离线全量安装** —— 理由见文末排除表。

## P4 · Live 环境形态 — ✅ 已确定

**决定（D12）：极简形态 —— 开机直进安装器，不做全功能桌面。**

| 后果 | 说明 |
|---|---|
| 路径最短 | 开机 → 安装器，中间没有「先玩一会儿 Live 桌面」这一层 |
| **不再兼作救援盘** | 有意接受。需要救援的用户应当使用专门的救援介质；这一点要写进发布文档 |
| 自动登录仍然必须 | 与形态无关：Live 不应要求输密码。现在更进一步 —— 自动登录之后要**自动起安装器**。releng 已经铺好了这条链的骨架（`getty@tty1` 自动登录 + root 登录后执行的 `.automated_script.sh`），kiosk 的自启动可以挂在同一条链上，也可以改成 systemd 服务 |
| **联网配置不能省** | P3 是在线安装：「极简」不等于「什么都不装」。Wi-Fi 选择 + 密码输入是 Live 的最小功能集之一（详见 P3 的表） |
| 中文界面需要 CJK 字体 | `noto-fonts-cjk` 已在清单里。**输入法不需要**（安装器不需要中文输入）—— 但若安装器允许输入中文 SSID，这条要重新评估，记为小风险 |
| releng 继承的救援类包可以裁 | `clonezilla`、`testdisk`、`ddrescue`、`fsarchiver`、`partimage`、`memtest86+`、`gpart` 等在极简形态下没有用途。**裁剪清单待定** —— `packages.x86_64` 里这些包目前标着「从 releng 继承，勿动」 |
| 与 P5 / P6 联动 | Live 用什么把安装器画出来（纯 TTY / framebuffer / 最小 Wayland 会话）取决于 P6 的界面工具包；kiosk 还要能限制会话能力（P5 评估维度里的最后一条） |

**被否决的方案：全功能桌面的 Live 环境** —— 理由见文末排除表。

## P5 · 桌面环境选型 — 🚧 讨论中（路线已定）

**已经定的方向：交付桌面走 WM 路线，不做完整桌面环境（DE）。**

> 原话记录：「至少在做完 WM 版本之前，不会考虑 DE。」
>
> 这句话本身就是范围约束：DE **不是永久排除**，而是优先级排在 WM 版本之后 ——
> 它省掉了每一轮都从头比较 Plasma / GNOME 的成本。

**候选收敛为两个：**

| 合成器 | 包名 | 撰写文档时的版本 | 说明 |
|---|---|---|---|
| niri | `niri` | 26.04-1 | 滚动平铺（scrollable tiling），配置用 KDL |
| Hyprland | `hyprland` | 0.56.2-3 | 动态平铺，配置用 hyprlang，社区与插件生态更大 |

（版本号是查 Arch 官方仓库 API 的快照，会随时间变化。）

**已不在候选内：** KDE Plasma / `kwin`（DE 路线）、`sway`、`labwc`。

**决定时要比的维度（目前全部未实测）：**

| 维度 | 为什么重要 | niri | Hyprland |
|---|---|---|---|
| NVIDIA + Wayland 稳定性 | **硬约束** —— D4 / D8 整条驱动线的前提 | 待测 | 待测 |
| 中文翻译完备度 | 「中文友好」是核心卖点 | 待查 | 待查 |
| fcitx5 集成 | Wayland 下输入法依赖 `text-input` 协议与环境变量，各合成器支持程度不同 | 待测 | 待测 |
| 配置与上手成本 | 目标用户是从 Windows 来的中文用户 | 待查 | 待查 |
| 与极简 Live 的配合 | P4 的 kiosk 会话可能要复用同一个合成器 | 待测 | 待测 |
| NVIDIA 专有驱动的已知坑 | `nvidia_drm.modeset=1`、显式同步等在各合成器下表现不同 | 待查 | 待查 |

**建议的定案方式：** 别在文档里比，装一次比。同一张 ISO 装到 `out/target.qcow2`，
再各上真机跑一轮，只测三件事 —— **驱动能亮、输入法能打字、中文能显示**。谁先跑通谁就是基线。

**与其它决策的关系：** P5 不阻塞「逻辑先于外壳」（P6 的第一步是纯脚本），
但**阻塞中文线的输入法集成与品牌化**（壁纸、主题、图标）。

## P6 · 安装程序方案 — ✅ 已确定

**决定（D14）：后端自研，技术栈定案如下。**

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3 | Live 里本来就有（`reflector` 依赖它，与 `archinstall` 无关）；测试与迭代最省事 |
| 界面 | Qt6 + PySide6 | `qt6-base` 已因 `fcitx5-qt` 在 Live 里；`pyside6` 在官方仓库 |
| kiosk 合成器 | `cage` | 单窗口全屏的 Wayland 合成器，专为这种场景而生；与 P5 的用户桌面（niri / Hyprland）不冲突 |
| 分区 | `python-pyparted` | 官方 Python 绑定（`archinstall` 同栈）；后续做双系统沿用同一条路 |
| 联网 | NetworkManager + `nmcli` | Issue #30：`iwctl` 不好用；安装器直接调命令行 |
| 引导（装后系统） | systemd-boot | UEFI-only 下与 ISO 自身的 `uefi.systemd-boot` 一致，少维护一套 |

**v0.1 的范围（有意做小）：** UEFI + 整盘擦除 + GPT（ESP + ext4 单根）。
**不做**双系统、LUKS、BIOS 引导、btrfs 子卷、LVM、离线安装 —— 排进里程碑，但第一版不碰。

**为什么第一版敢整盘擦除：** [05-测试方法.md](05-测试方法.md) 第 8 节的红线是「不做无损 resize」，
而**动别人的分区表**才是真正会丢数据的操作。整盘擦除把风险关在自己的盘里，
也让分区层不必处理已有的畸形分区表。

**表里每一项都来自官方仓库**（`pyside6` / `qt6-wayland` / `cage` / `python-pyparted` / `networkmanager`），
不引入第三方源（D5）。

**候选的事实依据（撰写文档时实测）：**

- `python-pyparted`：官方 `extra/3.13.0-6`，依赖 `parted` + `python`，**`archinstall` 就依赖它**。
  （这一条早先写成「`pyparted` 不在官方仓库、AUR 也未收录」—— 那是查了旧包名，已修正）
- `kpmcore`：官方 `extra/26.08.1-1`，提供 `libkpmcore.so` 与两个 `qt6/plugins/kpmcore/*.so`
  （`pmsfdiskbackendplugin`、`pmdummybackendplugin`）—— 带 `libfdisk` 后端的 C++/Qt 库，**没有 Python 绑定**
- `cage`：官方 `extra/0.3.1-1`（wlroots）；`qt6-wayland` 6.11.2-1、`pyside6` 6.11.2-1
- `systemd-repart`：随 systemd 261 自带，声明式配置 —— **本轮没选它**：整盘场景下 `pyparted` 更直接，
  而它帮不上双系统的忙（不缩小已有分区）
- `calamares` / `calamares-git`：AUR `3.4.2-2` / `3.4.2.r4.g841b47857-1`（votes=6 / 3，pop 均为 0.00），
  依赖全部在官方仓库，只有本体在 AUR —— 采用它就得自己接手维护

**不随技术栈变化的三条约束：**

1. **逻辑先于外壳**（[01-概念模型.md](01-概念模型.md) 第 7.4 节）：先把「分区 → 装包 → 配置 → 写引导」
   写成命令行脚本并在 QEMU 上跑通，再套界面。技术栈怎么选都不会让这部分返工。
2. **第一版不做无损 resize**（[05-测试方法.md](05-测试方法.md) 第 8 节）：这是数据丢失风险最高的一类操作；
   「完全从零写分区逻辑」也已在排除表里。
3. **分区测试只在虚拟盘上做**，真机用独立硬盘。

**里程碑与验收：** 见 [installer-roadmap.md](../work/installer-roadmap.md) ——
M0 骨架 → M1 逻辑闭环（无界面，最高优先）→ M2 Qt6 前端 → M3 装后系统 → M4 联网与镜像 → M5 发布。

## P7 · 「可变」的确切含义 — ✅ 已确定

**决定（D7）：「可变」指滚动更新，交付形态是装到硬盘的传统发行版。**

**背景：** 这个词有两种可能解释，工程量差距很大：

| 解释 | 含义 | 工作量 |
|---|---|---|
| **A. 滚动更新** ✅ | 装完的系统能正常 `pacman -Syu`，不被锁死版本 | 低，Arch 天然如此 |
| B. Live 持久化 | U 盘本身就是系统，改动会保存下来 | 高，需要 overlayfs + 持久分区（`cow_spaces` 机制） |

**选 A 的直接后果：**

- **安装器是必需组件** —— 交付物是 ISO + 安装流程，不是可持久化的 U 盘
- 本套文档按 A 编写，**全部有效，无需返工**
- 不需要设计 Live 环境的持久化分区与 overlay 容量管理
- 但必须保证装后系统能长期滚动升级（见 [05-测试方法.md](05-测试方法.md) 检查点 6）

**与 P4 的叠加：** 选 B（Live 持久化）时，Live 环境本身就是产品，必须做成全功能桌面；
选 A + P4（极简 kiosk）之后，Live 只是安装器的载体 —— 两者是一致的。

## P8 · NVIDIA 覆盖范围 — ✅ 已确定

**决定（D8）：只需覆盖 Turing 及更新架构。两位长期开发者的显卡（Blackwell / RTX 50 系、Ada Lovelace / RTX 40 系）都落在这个范围内。**

**背景：** NVIDIA 590 起，主线驱动包切换到 Open Kernel Modules，**同时移除了 Pascal 及更老架构的支持**（见 [04-架构决策.md](04-架构决策.md) 第一部分）。

**选定的方案与当初评估的对比：**

| 选择 | 后果 | 本项目 |
|---|---|---|
| **只支持 Turing 及更新** | 实现最简单 | ✅ **采用** |
| 同时提供 legacy 分支 | ISO 体积增加；需 udev 规则按硬件选择模块 | ❌ 不做 |
| 不预装，提示用户自行安装 | 违背「开箱可用」的初衷 | ❌ 不做 |

**技术确认：Blackwell（RTX 50 系）属于 Turing 及更新的范围，`nvidia-open` 完全支持**，无需任何 legacy 处理。

**保留的注意事项（P2 已定为对外发布，这条现在是必做项）：** 发布说明中必须写明
老显卡用户（GTX 10 系及以前）无法在此发行版上使用 NVIDIA 专有驱动。

## P9 · 发行版本号制度 — ✅ 已确定

**决定（D13）：双轨 —— ISO 产物名继续用构建日期；语义版号只出现在 GitHub 侧，用来让用户了解开发进度。**

| 位置 | 用什么 | 例子 |
|---|---|---|
| ISO 文件名 / `iso_version` / 卷标 | **构建日期**（现状，一行不改） | `miplinux-2026.09.18-x86_64.iso` |
| git tag + GitHub Release | **语义版号 `v0.x.y`** | `v0.1.0` |
| ISO 内部 | **不含语义号** | 不新增版本文件，`profiledef.sh` 不用动 |

**进位规则：** `0.x` 的 `x` 随**里程碑**进位，`y` 随该里程碑内的**对外发布次数**递增
（主版本保持 `0`，表示尚未到 1.0 稳定）。tag 打在 commit 上，Release 说明里写清
「这个语义号对应哪一天构建的产物、之后 main 上的改动未包含」——
语义号与产物的对应关系由**发布者声明**，而不是由构建自动带出。

**为什么不让语义号进 ISO：** Arch 是滚动发行版，**同一天重建的 ISO 内容都不同**，
日期才是产物的真实指纹；语义号是给「进度」贴的标签，两者口径不同，
混在一起会让「这份 ISO 到底是哪来的」变得说不清。

**为什么保留日期口径：** 维护成本为零；并且与 A7 的体积 / 耗时数据同口径（按天对比）。
`check-identity.sh` 不校验版本段格式，这条决定不会让它变红。

**还没做的：** 第一个 tag 还没打；里程碑与语义号的对应表、Release 说明模板都还没写。

## P10 · 包清单的组织方式 — 🚧 方向已明，未定案

**问题：D6 说「同一份包清单供 Live 环境与装后系统共用」。P3（在线安装）与 P4（极简 kiosk）定案后，这句话不再字面成立。**

| 环境 | 需要什么 | 不需要什么 |
|---|---|---|
| **Live**（极简，清单写死） | 安装器及其依赖、联网配置、CJK 字体、分区与装包工具、**N 卡驱动** | WM / 桌面、输入法、音频、浏览器 —— 装后系统要装什么不写死在 Live 清单里 |
| **装后系统**（更大） | 装后基础清单（能启动、能升级的最小集）+ **用户在安装器里勾选的应用**（装包阶段按勾选安装） | 安装器本身及其依赖（`cage` / `pyside6` 等 Live 专属件） |

**为什么不能就这么放着：** D6 的理由（防止「Live 里能用、装完不能用」）**依然成立** ——
它是一条**一致性**要求，不是「只能有一个文件」的要求。真正的风险是两份清单各写各的，
最后变成「Live 能跑、装后系统缺包」。

**候选处理方式：**

| 方案 | 说明 | 代价 |
|---|---|---|
| A. 两份清单 + 一套规则 | 都进 git：**Live 精简清单**（写死）+ **装后基础清单** + **应用目录**（用户在安装器里勾选的应用清单）；D6 重述为「唯一来源、禁止手写第二份清单」；三者关系写进 [03-项目结构.md](03-项目结构.md) | 要明确「基础 / 应用 / Live 独有」规则与勾选界面，并让检查脚本能验 |
| B. 仍只维护一份 | Live 也装全量包，只是界面极简 | ISO 体积回到全量，与 P3 / P4 的初衷相抵 |
| C. 一份全量 + 一份差异清单 | 由脚本派生 Live 清单 | 多一层派生逻辑，排查「这个包是谁带进来的」变难 |

**本次不动 D6**，先记在这里。定案后再改 README 决策表与 [03-项目结构.md](03-项目结构.md) 第 7.1 节。

> **驱动已落在 Live 一侧：** `nvidia-open` / `nvidia-utils` 写进 `profile/packages.x86_64`（即上表 Live 一列）——
> 真机验证要先在 Live 里拿到「驱动能加载」的证据。装后系统装什么不在这里：由装后基础清单 +
> 用户在安装器里勾选的应用决定（M1 已有一份**临时**目标清单充当装后基础清单）。

**连带受影响的文档：** [04-架构决策.md](04-架构决策.md) 第 1.6 节 ——
「驱动由安装器装进装后系统」这句话，成立的前提就是有一份写明了装什么的清单（P10 要回答的正是它放在哪）。

**现状证据（静态）：**

- 两份清单事实存在：Live 清单（`profile/packages.x86_64`）已含中文三件套与 `nvidia-open` /
  `nvidia-utils`；目标清单（`installer/backend/mipl_installer/data/target-packages.x86_64`）
  只有 base / linux / … 最小集 —— 装后系统静态上没有中文字体与输入法；
  QEMU 实测进展见 [tech/05](../work/tech/05-装后系统验证.md) §3。
- `packages.py` 的 `read_package_list` 已把「拿 Live 清单当装后清单」判为错误 —— 两份清单的
  墙已经立起来，缺的是规则，不是墙。

**已经明确的方向（未定案）：**

1. 两份清单各司其职：**Live 精简**（`profile/packages.x86_64` 继续瘦身，按 P4 的裁剪清单）、
   **装后更大**；
2. **installer 询问用户装哪些应用** —— 装后系统的应用集合不写死：装后基础清单（能启动、能升级）
   + 用户在安装器里勾选的应用，勾选结果由装包阶段的脚本安装；
3. Live 的 `packages.x86_64` **可以写死** —— 「写死」指这份清单描述的是 Live 环境本身、装什么不由用户勾选决定，不是说这份文件以后不能改（P4 的裁剪清单还没落，它显然还会改）。装完之后还能通过脚本补装应用 —— 用户附加程序由装包阶段的脚本安装（同第 2 条），与「写死」不矛盾。

**前后文一致性的三处修正：**

| 前文 | 现状 / 冲突 | 修正口径 |
|---|---|---|
| P4：「输入法不需要（安装器不需要中文输入）」 | Live 清单现在带着 fcitx5 系（09-19 线 C 并入的历史现状），与 P4 相抵 | 按 P4 口径，fcitx5 系不属于 Live 功能集，随 P10 落定移出 Live 清单、归入装后一侧 |
| P6 / D14：「`qt6-base` 已因 `fcitx5-qt` 在 Live 里」 | fcitx5 系移出 Live 后，这条选型理由的前提消失 | Live 清单要**显式**写 `qt6-base`（安装器 UI 依赖它），否则 D14 的理由与清单脱节 |
| 断言示例「Live 有 fcitx5 则装后必须有」 | 与「用户可以勾选不装」矛盾 | 改为：**基础集合两边一致**；应用目录里的包两边都不默认装，只有用户勾选才由装包阶段安装 |

**逐候选影响面：**

| 候选 | 涉及文件 | 检查脚本怎么验 | 主要代价 |
|---|---|---|---|
| A 两份清单 + 一套规则 | 装后基础清单落位（`data/` 或 `profile/`？）、应用目录形态、[03-项目结构](03-项目结构.md) 7.1、[roadmap](../work/installer-roadmap.md) M3 行、`packages.py` 的拒绝逻辑改指向 | 断言「仓库里只有 Live 清单 + 装后基础清单 + 应用目录 + 规则文件」；断言基础集合两边一致；断言代码里没有手写包名 | 要定义基础 / 应用 / 独有规则与勾选界面，规则本身也要防漂移 |
| B 仍只维护一份 | 仅 `profile/packages.x86_64`；删 `packages.py` 的拒绝逻辑 | 无需新增，最省 | ISO 体积回全量、Live 装一堆用不上的（WM / 输入法），与 P3 / P4 相抵 |
| C 全量 + 差异派生 | 新增全量清单 + 派生脚本；Live 清单变生成产物 | 断言 Live = 全量 − 差异（可再生成比对） | 多一层派生，排查「谁带进来的包」变难 |

**D6 重述措辞草案（若走 A）：** 「包清单的唯一来源按环境分份：Live 精简清单（写死）+
装后基础清单 + 应用目录；用户在安装器里勾选的应用由装包阶段从应用目录读取、脚本安装；
任何代码内手写包名即破线。」

**倾向：** A —— 只有它同时保住 P3 / P4（Live 极简）与 D6 的初衷（两边一致），
并且「装后装什么应用」由用户在安装器里决定，不写死在任何一份清单里。
**定案：** 等维护者；定案时一并拍：装后基础清单落位（`data/` vs `profile/`）、应用目录的形态、
哪些包属于基础（如 `nvidia-open` 是否默认勾选）、D 编号怎么重述 ——
它决定 `read_package_list` 与勾选界面的改动面。H5 的清单落地随之执行。

## P11 · 第三方仓库政策 — 🚧 新增（待专门一轮）

**问题：两份 `pacman.conf`（构建用的 `profile/pacman.conf`、Live 与装后系统继承的 `airootfs/etc/pacman.conf`）都启用了 `[archlinuxcn]`，而且是这样写的：**

```
[archlinuxcn]
SigLevel = Optional TrustAll
```

**`TrustAll` 的意思是不校验签名。** 内部构建无所谓，但 D10 定了对外发布 —— 用户装完的系统里会带着一个不校验签名的第三方源。
而**装后系统的 `pacman.conf` 是安装器写的**（P6），所以安装器必须先知道写什么。

**三个候选：**

| 方案 | 说明 | 代价 |
|---|---|---|
| A. 收紧到签名校验 | 装 `archlinuxcn-keyring`，`SigLevel` 改为 `Required DatabaseOptional` | 装后系统多一个 keyring 包；首次 `pacman -Sy` 前必须已导入 key |
| B. 默认不启用，安装器里可选 | 装后系统默认只有官方源；要用的用户在安装器里勾选 | 安装器多一个开关；勾选后仍要处理 keyring |
| C. 保持现状 | 一行不改 | 对外发布时是明确的安全折扣，必须写进发布说明 |

**何时必须定：** M4（联网与镜像）之前 —— 见 [installer-roadmap.md](../work/installer-roadmap.md) 第 8 节。

## 附 · 已明确排除的方案

记录已否决的选项，避免重复讨论。

| 方案 | 否决理由 |
|---|---|
| fork CachyOS-Live-ISO | 绑定他人仓库结构，与项目目标冲突 |
| 使用 CachyOS 内核 | 需要挂载外部仓库，与「不依赖 CachyOS」的目标矛盾 |
| 使用 DKMS 作为 Live 环境方案 | squashfs 只读，Live 中编译占用内存和时间 |
| 完全从零编写安装器的分区逻辑 | 无损 resize 等操作的缺陷会造成数据丢失，风险不可接受 |
| 在宿主机直接运行 `mkarchiso` | 会静默引入宿主发行版的软件源 |
| 在 systemd-nspawn 中测试 ISO | nspawn 不具备「引导」能力 |
| 使用 stage3 / bootstrap tarball 作为交付物 | 不是可引导介质，无法满足「插上 U 盘就能装」 |
| **离线全量安装**（P3） | ISO 3–5 GB；要处理包缓存、`CacheDir`、压缩策略；而这些投入与「国内源本来就要做成默认」这一既有目标重复。在线安装的体积与迭代速度更划算 |
| **全功能桌面的 Live 环境**（P4） | ISO 更大、开机更慢，与「开机即装、路径最短」冲突；救援用途改由专门的救援介质承担 |
| **完整桌面环境（KDE Plasma 等）作为交付桌面**（P5） | 已确定 WM 路线。不做「先 Plasma、以后再换 WM」的两步走 —— 那等于把中文线做两遍。**做完 WM 版本之前不考虑 DE** |
| **Calamares 作为安装器**（P6） | 本体在 AUR（votes=6），需要自建仓库分发 → 背上包维护；P6 定为后端自研后这个前提消失。也避免把分区能力交给一个我们无法修的第三方组件 |
| **安装器后端用 Rust / Go**（P6） | 静态二进制要自建仓库分发，撞 D5 与 P2 的发布成本；而 Python 已经在 Live 里（`reflector` 依赖它）—— 换语言没有收益 |
| **把安装器源码放进独立仓库**（P6） | ISO 构建要跨仓库取源码，破坏「产物 ⇄ commit 一一对应」；触发迁出的条件写在 [installer-roadmap.md](../work/installer-roadmap.md) |
| **v0.1 用 C++/Qt6 + kpmcore 做分区**（P6） | 要编译、迭代慢；kpmcore 的强项（缩小已有分区）v0.1 用不到 —— 留到双系统里程碑再评估 |
| **语义版号替代产物名里的日期**（P9） | 滚动发行版里同一天重建的产物都不同，日期才是真实指纹；语义号只用于对外沟通进度 |
