## P1 · 发行版名称

**现状：** 暂用 MipLinux（来自工作目录名）。

**影响：** 名称会渗透到很多地方，改起来不轻松：

- `profiledef.sh` 的 `iso_name`、`iso_publisher`、`iso_application`
- `iso_label`（会被写入引导参数）
- `/etc/os-release`
- 壁纸、logo、品牌资源
- 仓库名、文档标题

**建议：** 在动手写配置之前定下来。虽然可以后期全局替换，但 `iso_label` 涉及引导参数，改动需要重新验证引导。

## P2 · 目标范围

**问题：只给自己和朋友用，还是要对外发布？**

**影响：**

| 维度 | 自用 | 对外发布 |
|---|---|---|
| 签名 | 不需要 | 需要 GPG 签名与校验和 |
| 软件仓库 | 不需要 | 需要（至少用于分发 Calamares 或自有包） |
| 升级路径 | 无要求 | 用户能从旧版本升级 |
| 文档 | 随意 | 需要完整的中文安装与使用文档 |
| 硬件兼容 | 只需覆盖两人的机器 | 需要覆盖各种显卡、磁盘、主板 |
| 缺陷容忍度 | 高 | 低 |

**说明：** 这个决定影响几乎所有后续工作的严格程度。**建议在开始写安装器之前确定。**

## P3 · ISO 形态

**问题：在线安装，还是离线全量安装？**

| | 在线安装 | 离线全量安装 |
|---|---|---|
| ISO 体积 | ~1 GB | 3–5 GB |
| 装机前提 | 必须联网 | 不联网也能装完 |
| 开发速度 | 快 | 慢（需处理包缓存） |
| 对中文用户的价值 | 依赖国内源速度 | **插上 U 盘就能装完，体验最好** |

**技术影响：**

离线方案需要额外处理：

- 包缓存目录的构建与复用
- `pacman.conf` 中 `CacheDir` 的配置
- ISO 体积与压缩策略的权衡

**相关观察：** 离线安装是真正解决「预装 N 卡驱动」这个痛点的形态——因为驱动包必须在 ISO 里。在线安装虽然也能预装，但如果用户网络不畅，体验会打折。

## P4 · Live 环境形态

**问题：Live 环境是全功能桌面，还是开机直弹安装器的极简形态？**

| | 全功能桌面 | 极简 kiosk |
|---|---|---|
| 用户体验 | 可以先试用、检查硬件、上网 | 开机即安装，路径最短 |
| 作为救援盘 | 可用 | 不可用 |
| ISO 体积 | 较大 | 较小 |
| 开机速度 | 较慢 | 较快 |

**共同点：** 两种方案都**必须配置自动登录**——Live 环境不应该要求输入密码。

**注：** 这个决定与 P5（桌面环境选型）相关，但不是同一个问题。

## P6 · 安装程序方案

**现状：** 已讨论过四个方案，尚未决定。

| 方案 | 你写什么 | 依赖 | 主要代价 |
|---|---|---|---|
| **Calamares** | YAML + shell | 本体在 AUR | 需自建仓库分发，背上包维护 |
| **自研 + systemd-repart** | GUI + shell | 纯官方源 | 双系统支持弱（不擅长缩小已有分区） |
| **自研 + kpmcore** | GUI + shell + C++ 胶水 | 官方库但有 ABI 风险 | kpmcore 无 Python 绑定 |
| **自研 + parted/sfdisk** | GUI + shell | 纯官方源 | 分区逻辑需自己兜底 |

**相关事实（实测）：**

- `calamares` 在 AUR，`3.4.2-2`，votes=6，pop=0.00；其依赖全部在官方仓库
- `archinstall` 在官方仓库 `extra/4.4-1`，且**已在 releng 包清单中**
- `kpmcore` 在官方仓库 `extra/26.08.1-1`，是 C++/Qt 库，**无 Python 绑定**
- `pyparted` 既不在官方仓库，AUR 也未收录
- `systemd-repart` 随 systemd 261 自带，声明式配置

**共同点：** 无论选哪种方案，装系统的实际逻辑（分区 → 装包 → 配置 → 写引导）是同一套。

**建议的推进方式（见 [01-概念模型.md](01-概念模型.md) 第 7.4 节「逻辑先于外壳」）：**

1. 先写逻辑脚本（`pacstrap` + `arch-chroot` 配置 + 引导），用命令行跑通并在 QEMU 验证
2. 再写分区逻辑
3. 最后才写界面

这样界面方案的变更不会导致返工。

**另有中间选项：** 先用 `archinstall`（已在 ISO 中）把逻辑跑通，再决定是否套 Calamares 的壳。

## P7 · 「可变」的确切含义 — ✅ 已确定

**决定（D7）：「可变」指滚动更新，交付形态是装到硬盘的传统发行版。**

**背景：** 这个词有两种可能解释，工程量差距很大：

| 解释 | 含义 | 工作量 |
|---|---|---|
| **A. 滚动更新** ✅ | 装完的系统能正常 `pacman -Syu`，不被锁死版本 | 低，Arch 天然如此 |
| B. Live 持久化 | U 盘本身就是系统，改动会保存下来 | 高，需要 overlayfs + 持久分区（`cow_spaces` 机制） |

**选 A 的直接后果：**

- **安装器是必需组件** —— 交付物是 ISO + 安装流程，不是可持久化的 U 盘
- 本套文档按 A 编写，**全部有效，无需返工**
- 不需要设计 Live 环境的持久化分区与 overlay 容量管理
- 但必须保证装后系统能长期滚动升级（见 [05-测试方法.md](05-测试方法.md) 检查点 6）

## P8 · NVIDIA 覆盖范围 — ✅ 已确定

**决定（D8）：只需覆盖 Turing 及更新架构。两位开发者使用的都是 Blackwell（RTX 50 系）。**

**背景：** NVIDIA 590 起，主线驱动包切换到 Open Kernel Modules，**同时移除了 Pascal 及更老架构的支持**（见 [04-架构决策.md](04-架构决策.md) 第一部分）。

**选定的方案与当初评估的对比：**

| 选择 | 后果 | 本项目 |
|---|---|---|
| **只支持 Turing 及更新** | 实现最简单 | ✅ **采用** |
| 同时提供 legacy 分支 | ISO 体积增加；需 udev 规则按硬件选择模块 | ❌ 不做 |
| 不预装，提示用户自行安装 | 违背「开箱可用」的初衷 | ❌ 不做 |

**技术确认：Blackwell（RTX 50 系）属于 Turing 及更新的范围，`nvidia-open` 完全支持**，无需任何 legacy 处理。

**保留的注意事项：** 若未来 P2 决定对外发布，老显卡用户（GTX 10 系及以前）将无法在此发行版上使用 NVIDIA 专有驱动，这一点需要在发布文档中说明。

## 附 · 已明确排除的方案

记录已否决的选项，避免重复讨论。

| 方案 | 否决理由 |
|---|---|
| fork CachyOS-Live-ISO | 绑定他人仓库结构，与项目目标冲突 |
| 使用 CachyOS 内核 | 需要挂载外部仓库，与「不依赖 CachyOS」的目标矛盾 |
| 使用 DKMS 作为 Live 环境方案 | squashfs 只读，Live 中编译占用内存和时间 |
| 完全从零编写安装器的分区逻辑 | 无损 resize 等操作的缺陷会造成数据丢失，风险不可接受 |
| 在宿主机直接运行 `mkarchiso` | 会静默引入宿主发行版的软件源 |
| 在 systemd-nspawn 中测试 ISO | nspawn 不具备「引导」能力 |
| 使用 stage3 / bootstrap tarball 作为交付物 | 不是可引导介质，无法满足「插上 U 盘就能装」 |
